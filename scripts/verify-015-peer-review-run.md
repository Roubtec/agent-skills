# verify-015-peer-review-run — exercise the canonical peer step and report effective strength

This is a harness-neutral prose check for an agent, not a CI script. Exercise the peer step from your own `review-cycle` rendering, or the byte-identical `review-cycle-core` embedded in `wf-address-tasks.js`, against a non-empty trivial committed change in a scratch worktree. State which harness and provider you exercised; one harness's observation never stands in for the other side.

## Procedure

1. Read the canonical peer block for your harness and follow its launch shape exactly, including its artifact placement and explicit strength flags. Do not add a model or effort flag of your own.
2. Use the committed prompt guidance: no network access, verbatim thread/diff evidence, and a response that states whether tests were executed or verification was static. On the Claude-provider helper path, resolve the effective base and review tip to full commit OIDs, create the canonical read-only `diff-evidence.txt` outside the worktree with that exact `base..tip` log and `base...tip` diff, name its absolute path and both OIDs in the prompt, and require the peer's final response to identify a unique token selected from the committed diff already in that evidence. Do not add content to the artifact after the exact log and diff. Do not add a caller `--add-dir` flag either: the current helper exposes none, and its Claude adapter grants the worktree itself; this check must prove the native Read tool can read the separately named evidence path in the unique invocation directory.
3. Record the launch shape, result outcome, artifact directory, diff-evidence path and mode, effective model, effective effort, the token the peer read from the evidence, and whether the outcome gate behaved as documented. Also exercise an `unavailable` result where feasible (for example in a deliberately logged-out disposable environment) and confirm it remains non-blocking.
4. Report PASS or FAIL against the provider-specific expectations below and name the other provider as unexercised by this run. The Claude-provider helper path fails this check if the peer reaches a verdict without demonstrating that it read the named evidence, even when the helper reports `passed` and the strength fields match.

## Provider-specific observations

- **Claude peer from the Codex-side rendering:** this is the converted helper path. Read `model`, `effort`, `outcome`, `reason`, and `artifactDir` from the final `powbox.peer-review-run/v1` JSON line. PASS requires `model: "opus"`, `effort: "medium"`, mode `400` on the uniquely allocated evidence artifact, and the peer's correct report of its token; read the full review prose from `artifactDir` when the outcome is `passed` or `issues`. A raw launch is permitted only when `command -v peer-review-run` fails; there the main `modelUsage.canonicalModel` must resolve to an Opus-class model, while the raw Claude JSON envelope exposes no effort field, so report effort as unobservable rather than guessing.
- **Codex peer from the Claude-side rendering and both workflow cores:** task 015 deliberately retains the pinned raw path until `peer-review-run` can carry the configured Codex model through its config isolation. Read `model:` and `reasoning effort:` from the separately captured raw-launch stderr header. PASS requires the configured high-capability model from `~/.codex/config.toml` and `reasoning effort: medium`; a bare default or `reasoning effort: none` fails. When the configured-model passthrough eventually lands and this rendering converts, read both values from the helper JSON instead; `model: null` is not a passing configured-model observation.

## Report shape

Report: harness; canonical source exercised (`review-cycle` prose, `wf-review-cycle.js`, or the `wf-address-tasks.js` embedded copy); provider; helper or retained-raw/fallback launch; outcome; artifact directory; diff-evidence path, mode, pinned range, and observed token where applicable; observed model; observed effort; verification statement (`executed` with commands, or `static`); non-blocking-unavailability result if exercised; PASS/FAIL; and the provider this run leaves unexercised.
