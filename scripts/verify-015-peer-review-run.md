# verify-015-peer-review-run — exercise the canonical peer step and report effective strength

This is a harness-neutral prose check for an agent, not a CI script. Exercise the peer step from your own `review-cycle` rendering, or the byte-identical `review-cycle-core` embedded in `wf-address-tasks.js`, against a non-empty trivial committed change in a scratch worktree. State which harness and provider you exercised; one harness's observation never stands in for the other side.

## Procedure

1. Read the canonical peer block for your harness and follow its launch shape exactly, including its artifact placement and explicit strength flags. Do not add a model or effort flag of your own.
2. Use the committed prompt guidance: no network access, verbatim thread/diff evidence, and a response that states whether tests were executed or verification was static. On the Claude-provider helper path, resolve the effective base and review tip to full commit OIDs, create the canonical read-only `diff-evidence.txt` audit copy outside the worktree with that exact `base..tip` log and `base...tip` diff, and construct the prompt through the documented static-heredoc plus literal generated-data contract. Embed both pinned OIDs and the complete audit-copy bytes between `BEGIN EMBEDDED GIT EVIDENCE` and `END EMBEDDED GIT EVIDENCE`; do not ask the provider to read the external file. Require the peer's final response to quote `EVIDENCE_BASE_OID: <full OID>`, `EVIDENCE_TIP_OID: <full OID>`, and `EVIDENCE_TOKEN: <token>`, with an exact distinctive non-whitespace token selected from an added or removed line and occurring exactly once inside the embedded evidence section. Do not reveal an expected token in the prompt, and do not add content to the audit copy after the exact log and diff. Do not add a caller `--add-dir` flag: the current helper exposes none, and this check proves the verdict from evidence already delivered in the prompt rather than from an incidental out-of-worktree permission.
3. Exercise the evidence failure gate twice on disposable copies without accepting either copy's verdict: first remove or alter either quoted OID proof line from an otherwise valid `passed` or `issues` review artifact; then remove the `EVIDENCE_TOKEN:` line or replace its token with one absent from or repeated in the prompt's embedded evidence section. Each must normalize to `forfeited` with reason exactly `embedded diff evidence or proof absent`. A helper-reported verdict, a readable audit copy, or correct strength metadata must not override either negative control.
4. Exercise lifecycle negative controls without targeting a real provider: use a scratch fake `/proc/<pid>/stat` fixture whose comm contains spaces and `)`, persist its field-22 start time, then change only that field while retaining the PID/PGID number. Every PID and group probe/signal must treat the changed or missing record as the original process being dead and record no `kill`; a matching record must resolve the direct PID and deliberately-established negative PGID as documented. For the retained raw Codex path, use a fake provider that ignores TERM to observe the bounded KILL, then one that survives KILL simulation to confirm the cycle stops/escalates and never retries or advances. The committed `test-review-cycle-retirement.mjs` runs the parser/reuse controls and the first-wave shared-preflight concurrency/reset controls on both workflow cores; record that suite's result here.
5. Record the launch shape, result outcome, artifact directory, diff-evidence audit path and mode, the pinned base and tip OIDs quoted by the peer, effective model, effective effort, the token the peer copied from the embedded evidence, the two evidence-negative outcomes, the PID/PGID reuse and raw-provider death-control outcomes, the concurrent-preflight suite result, and whether every outcome gate behaved as documented. Also exercise an `unavailable` result where feasible (for example in a deliberately logged-out disposable environment) and confirm it remains non-blocking.
6. Report PASS or FAIL against the provider-specific expectations below and name the other provider as unexercised by this run. The Claude-provider helper path fails this check if the peer reaches a verdict without demonstrating that it used the embedded pinned evidence, even when the helper reports `passed` and the strength fields match.

Read `model`, `effort`, `outcome`, `reason`, and `artifactDir` from the final `powbox.peer-review-run/v1` JSON line. PASS requires `model: "opus"`, `effort: "medium"`, mode `400` on the uniquely allocated audit artifact, exact `EVIDENCE_BASE_OID:` and `EVIDENCE_TIP_OID:` lines matching the values embedded in the prompt, and an `EVIDENCE_TOKEN:` proof whose exact token occurs once on an added or removed line inside that prompt's marked evidence section; read the full review prose from `artifactDir` when the outcome is `passed` or `issues`, but accept its verdict only after those embedded-evidence checks. When the configured-model passthrough eventually lands and this rendering converts, read both values from the helper JSON instead; `model: null` is not a passing configured-model observation.

## Report shape

Report: harness; canonical source exercised (`review-cycle` prose, `wf-review-cycle.js`, or the `wf-address-tasks.js` embedded copy); provider; helper or retained-raw/fallback launch; outcome; artifact directory; diff-evidence audit path and mode; exact pinned base and tip OIDs quoted from the embedded prompt; observed `EVIDENCE_TOKEN:` where applicable; mismatched-OID and absent/invalid-token outcomes; PID/PGID reuse and raw-provider death-control outcomes; concurrent-preflight/reset suite result; observed model; observed effort; verification statement (`executed` with commands, or `static`); non-blocking-unavailability result if exercised; PASS/FAIL; and the provider this run leaves unexercised.
