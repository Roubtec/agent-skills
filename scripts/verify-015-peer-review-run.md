# verify-015-peer-review-run — exercise the canonical peer step and report effective strength

This is a harness-neutral prose check for an agent, not a CI script. Exercise the peer step from your own `review-cycle` rendering, or the byte-identical `review-cycle-core` embedded in `wf-address-tasks.js`, against a non-empty trivial committed change in a scratch worktree. State which harness and provider you exercised; one harness's observation never stands in for the other side.

## Procedure

1. Read the canonical peer block for your harness and follow its launch shape exactly, including its artifact placement and explicit strength flags. Do not add a model or effort flag of your own.
2. Use the committed prompt guidance: no network access, verbatim thread/diff evidence, and a response that states whether tests were executed or verification was static. On the Claude-provider helper path, resolve the effective base and review tip to full commit OIDs, create the canonical read-only `diff-evidence.txt` outside the worktree with that exact `base..tip` log and `base...tip` diff, name its absolute path and both OIDs in the prompt, and require the peer's final response to report `EVIDENCE_TOKEN: <token>` with an exact distinctive non-whitespace token selected from an added or removed line and occurring exactly once in that evidence. Do not reveal an expected token in the prompt, and do not add content to the artifact after the exact log and diff. Do not add a caller `--add-dir` flag either: the current helper exposes none, and its Claude adapter grants the worktree itself; this check must prove the native Read tool can read the separately named evidence path in the unique invocation directory.
3. Exercise the evidence failure gate twice on disposable copies without accepting either copy's verdict: first remove the `EVIDENCE_TOKEN:` proof line from an otherwise valid `passed` or `issues` review artifact; then use a missing/denied evidence path (or replace the reported token with one absent from or repeated in the diff artifact). Each must normalize to `forfeited` with reason exactly `diff evidence unreadable or EVIDENCE_TOKEN absent`. A helper-reported verdict or correct strength metadata must not override either negative control.
4. Exercise lifecycle negative controls without targeting a real provider: use a scratch fake `/proc/<pid>/stat` fixture whose comm contains spaces and `)`, persist its field-22 start time, then change only that field while retaining the PID/PGID number. Every PID and group probe/signal must treat the changed or missing record as the original process being dead and record no `kill`; a matching record must resolve the direct PID and deliberately-established negative PGID as documented. For the retained raw Codex path, use a fake provider that ignores TERM to observe the bounded KILL, then one that survives KILL simulation to confirm the cycle stops/escalates and never retries or advances. The committed `test-review-cycle-retirement.mjs` runs the parser/reuse controls and the first-wave shared-preflight concurrency/reset controls on both workflow cores; record that suite's result here.
5. Record the launch shape, result outcome, artifact directory, diff-evidence path and mode, effective model, effective effort, the token the peer read from the evidence, the two evidence-negative outcomes, the PID/PGID reuse and raw-provider death-control outcomes, the concurrent-preflight suite result, and whether every outcome gate behaved as documented. Also exercise an `unavailable` result where feasible (for example in a deliberately logged-out disposable environment) and confirm it remains non-blocking.
6. Report PASS or FAIL against the provider-specific expectations below and name the other provider as unexercised by this run. The Claude-provider helper path fails this check if the peer reaches a verdict without demonstrating that it read the named evidence, even when the helper reports `passed` and the strength fields match.
