# Task Management

Numbered tasks use a three-digit number, optionally followed by a lowercase letter suffix, e.g. `001`, `001a`, `042b`. Follow-up tasks (that are out of scope for an existing PR but relate to it) can be queued under the parent's number with a letter suffix: 001a, 001b, etc. for tasks related to task 001, for example. This allows us to preserve the follow-up intent and implement it soon after the original task has been addressed satisfactorily enough. Generic follow-up tasks (that arose from batch reviews or other general observations) can be added to the end of the queue.

Once a task is completed and merged, it is moved to "tasks/done/" during the next task sweep. Cross-referenced tasks could be found in either folder, which is why we use task numbers and not links to point at other tasks. Specced tasks we do not currently intend to schedule belong in "tasks/deferred/", such as work that depends on uncertain functionality, addresses a condition that cannot occur yet or has not manifested and would be costly to fix, or a task that awaits a spike. A planned task with unmet prerequisites stays in "tasks/" with those prerequisites stated so its ordering remains visible. A deferred task that we decide to act on gets moved to "tasks/" to be picked up by the next implementation wave.

Cite code in a task by naming the symbol or scope that holds it — function, class, namespace, module, exported constant — or another unique string such as a heading, within a named file or folder, and let the reader grep for it; do not cite line numbers, which rot on the next rebase or any edit above them (task 015b exists solely to repair one task's stale ones). A line number is acceptable only where nothing stable names the thing referenced, and the task must then say so and stamp what the numbers are as of, the way tasks 012b and 014a do. Citations already written stay as written — this governs what gets written from here on.

Avoid cross-linking tasks with hyperlinks; use task numbers to cross-reference so that task file churn (archival to done, promotion from deferred, etc.) does not break links. Task numbers are stable and unique, and the task file itself is the canonical source of truth for its content. Any task file can be grepped by the task number in "tasks/".
