# 015 — Adopt the peer-review-run contract in the review skills' peer steps

## Why this task exists

The post-014 canonical peer step still documents a raw backgrounded launch (`codex exec --sandbox read-only --cd "$worktree" -o "$outfile" … &`, `plugins/dev-skills/skills/review-cycle/SKILL.md:101-103`), which `address-review`, `address-reviews`, `address-tasks`, `address-tasks-serialized`, and `resolve-open-questions` now consume by reference rather than copying. Months of field use across kalm2, jabko, Scribz, and powbox sessions show that pattern is a reliability tarpit every orchestrator re-hits:

- run through a harness Bash tool, the wrapping shell exits immediately and the completion notification describes the **launcher**, not the peer — every launch needed a `nohup … &` workaround plus a `pgrep` liveness verification round-trip;
- `pgrep -f "codex exec"` returns the entire multi-KB prompt from the process command line (34 KB in one liveness check), and `pkill -f <token>` has killed the killing shell itself when the token appeared in its own argv;
- prompts assembled in double-quoted shell variables were corrupted by backtick/`$( )` expansion;
- a single foreground call capped by the Bash tool's 10-minute maximum silently forfeited the peer opinion on exactly the largest, most security-sensitive diffs (exit 143, no output file);
- an empty `-o` file is ambiguous between "still running", "finished but forfeited", and "crashed".

powbox now bakes `peer-review-run` (`/usr/local/bin/peer-review-run`), a provider-neutral runner that owns all of this: literal prompt-file handling (stdin, never shell-interpolated), read-only provider execution with config/hook isolation, process-group supervision with timeout, transient-only retry (auth/usage short-circuits to `unavailable`), reaping on every exit path, and a machine-readable result — final stdout line is one JSON object, schema `powbox.peer-review-run/v1`: `{ schema, provider, outcome, verdict, elapsedSeconds, exitStatus, attempts, retried, liveProgress, artifactDir, reason }`, `outcome ∈ passed | issues | unavailable | timeout | forfeited | failed`, exit 0 for any produced outcome. powbox's `docs/architecture.md` explicitly names this contract as the adoption boundary for these skills.

## Scope

Included:

- Replace the raw launch in the canonical `review-cycle` peer step and its workflow renderings with a `peer-review-run` invocation: `peer-review-run --provider codex --worktree "$worktree" --prompt-file "$promptfile" --artifact-root "$artifact_root" [--timeout N]` (the Claude-led rendering reviews with codex; the codex-side `review-cycle` mirror reviews with `--provider claude` — update the canonical renderings symmetrically, while consumers continue to import them).
- Map helper outcomes onto the skills' existing gate vocabulary: `issues`/`passed` feed the verdict logic unchanged; `unavailable`, `timeout`, `forfeited`, `failed` are the existing explicit non-blocking outcomes. The `artifactDir` points at the full review prose for verbatim relay to fixers.
- Keep the existing protocol semantics untouched: preflight-once, `peer-opinions=off`, grounding spot-check, blocking+minor gating, verbatim finding relay, peer never required for publication.
- **Carry the review-strength baseline across the swap, and pin effort at `medium`.** `medium` is the default and encouraged reasoning effort for every peer invocation. This is a maintainer decision taken after deliberation, recorded here because this is the live task that rewrites the peer steps, and it **supersedes the `high` effort** stated by 001's quality floor ("high or xhigh") and by 014's canonical peer step — both archived, both left as the historical record of what was delivered rather than rewritten. An implementer converting a peer step pins `medium` rather than transcribing the older value, and where a rendering is left on its raw launch, that launch is retuned to `medium` too, so the two paths do not disagree. **That raw-launch retune has already landed**, ahead of this task and in the same PR that recorded the decision: both `review-cycle` mirrors and the launch snippets in all three workflows already pin `medium`, as does the strength-verification script. So the level is settled and is not this task's work; what remains here is the helper swap itself, which must carry `medium` rather than re-derive it. Only the effort dimension moves. The model dimension is untouched — a high-capability tier, never an economy one, named by rolling alias or harness default and never by a dated model ID — and `xhigh` and `max` stay out. No remaining "high" in this bullet states a pinned effort: every effort pin below reads `medium`, and the rest refer to model capability, to the helper's own default, or to the superseded pin — read each for which of those it is. The reasoning about which dimensions each CLI gives a stable handle on is unaffected by the level chosen. The raw-launch snippets this task replaces pin review strength per invocation, in the provider-specific form each CLI offers: the codex peer pins effort (`-c model_reasoning_effort=medium`) and leaves the model to the peer's configured high-capability default, while the claude peer pins both (`--model opus --effort medium`), its model included because that side has a stable capability alias to pin — `opus` — where naming a codex model would mean hardcoding a concrete id that goes stale, and because a container may most recently have selected an economy tier there. Each form pins everything its CLI gives a stable handle on, precisely so no pinned dimension follows whichever value a container most recently selected in the shared `~/.claude/settings.json` or `~/.codex/config.toml`. The codex peer's model is the one dimension left unpinned, resting instead on the container's codex configuration, as the canonical Claude-led peer step now states outright (`plugins/dev-skills/skills/review-cycle/SKILL.md:81`); its consumers inherit that rule instead of restating it. `peer-review-run` as baked today carries **effort for both providers, and the model for claude only** — verified against the installed helper on 2026-08-08: it accepts `--model <ID>` and `--effort <LEVEL>`, defaults effort to `high` for both providers, re-injects `-c model_reasoning_effort=<effort>` inside its codex adapter precisely so that adapter's own `--ignore-user-config` cannot strip it, applies a `--model opus` default on the claude side, and reports the strength it actually applied as `model` and `effort` in its result. One dimension is still missing, and only on the codex side: `--ignore-user-config` discards `config.toml` entirely, which is what the codex form's unpinned model rests on, and the helper's `--model` default does not extend to that provider, so a codex peer launched through the helper reviews on whatever model codex defaults to bare. A snippet-for-snippet swap that names no flags therefore leaves the codex peer's model bare and both peers' effort on the helper's own default rather than on the pin, so name the flags explicitly on every converted step. Effort is passed explicitly on the helper path rather than left to the helper's own default of `high`: relying on that default was defensible while the pin was also `high`, and overshoots the pin now that it is `medium`. What the helper must still carry for the model is the container's configured high-capability model, not a literal id — 001's quality floor allows a rolling alias or the harness default and forbids dated model IDs in skill text, which is why the claude side pins the `opus` alias and the codex side names nothing. Whether powbox delivers that as a caller-supplied argument or by sparing the model from the config isolation is powbox's call. Reporting was the other half of 014's ask and it has landed: the helper's `model`/`effort` result fields state what it applied, so a passthrough this task swaps onto can be verified to have honoured the pin rather than trusted. The prerequisite therefore narrows rather than disappears, and it is **per provider**. For the **codex** peer — the Claude-led renderings' side — the swap must not land until the helper can carry that configured model; its addition is powbox-owned and out of scope here (see "Out of scope"), so file it against powbox first and treat it as a hard prerequisite of converting those peer steps, and if it is still unavailable when this task is picked up, keep them on their pinned raw launches and say so explicitly rather than accepting a silent model downgrade. For the **claude** peer — the codex-led renderings' side — **no prerequisite remains outstanding**: the helper carries `--model opus --effort medium` today and reports what it applied, so those canonical renderings convert unconditionally, with `--effort medium` stated explicitly rather than inherited. 014c records that claude-side decision on the `review-cycle` codex mirror; do not read an already-delivered effort passthrough as a blocker on either side.
- Add a **fallback** paragraph for environments without the helper (`command -v peer-review-run` fails): the hardened manual pattern — write the prompt via quoted heredoc (`<<'PROMPT'`), launch with `nohup … &` with stdin redirected (never left on the caller's terminal) and a unique per-attempt output path, check liveness without ever matching on the prompt text, signal the peer through the same identifier the liveness probe resolves to rather than a separately guessed one — resolving a pattern-based probe to a PID first and never signalling through the pattern itself with `pkill -f`. Resolving is not simply reading `pgrep -f`'s output: the launching shell's own command line contains the unique path too, and so may an ancestor, so an unfiltered match set includes processes whose death is the caller's — the same self-inflicted kill `pkill -f` already caused here, merely one step later. Require the match to be disambiguated before it is read as *either* an answer or a target, because the contamination is symmetric and hits the probe hardest: a later shell running the probe names the output path in the probe command itself, so that shell's own argv carries it and `pgrep` — which excludes only its own PID, never its parent — matches unconditionally. Left raw, the probe reports alive forever, a peer that died at second three burns the whole timeout, and the dead-peer branch below can never fire, because the set is never empty. So the disambiguated set *is* the liveness answer: drop the current shell and its ancestors, keep only a process that is the peer binary itself rather than a shell whose argv happens to carry the path, and then exactly one survivor means alive, none means dead, and more than one means indeterminate — probe again, and signal nothing. The launch can sidestep the ambiguity outright by recording the peer's PID at launch — under `nohup … &` the provider is `exec`ed, so `$!` is the peer's own PID — and persisting it for later shells to probe with `kill -0` and signal directly; that is the preferred shape for a tree writing the fallback fresh. It is emphatically *not* what the trees with an existing handoff do, and they must not be converted to it: they run the peer under `setsid --fork`, where `$!` is the wait supervisor rather than the peer, which is why they hand off a session-leader PGID instead — see the background bullet below. Signal a process **group** only where the launch deliberately established one: a plain `nohup … &` leaves the peer in the launching shell's group, so widening the target to that group would kill the caller — the same self-inflicted death `pkill -f` already caused. Never target a wait supervisor standing in for the peer it supervises. Treat a non-empty result artifact containing a `VERDICT:` line as authoritative, and never run the peer as a capped foreground call. Three of those rules take a provider-specific form, and each tree's paragraph states the form for its own peer provider: capture is `-o <path>` for codex and redirected stdout with a separate stderr file for Claude (`claude -p … > <stdout-file> 2> <stderr-file>`, never `2>&1`); stdin is `< /dev/null` for codex and `< "$prompt_file"` for Claude; liveness is a disambiguated `pgrep -f` match on the unique output path for codex, which `-o` places in the peer's own argv — or `kill -0` on a PID recorded at launch where the tree records one, which is preferred — and `kill -0` against the PID or process group established at launch for Claude — captured directly, or handed off by the launcher where the tree runs the peer under its own session leader — because Claude's output path is consumed by the shell's redirection and so never reaches the peer's own command line. Everything above in this bullet — the trigger condition, the hardening rules, and these three provider-specific forms — is what gets transcribed; the next bullet is background for the implementer, not skill text.
- Background for the three provider-specific rules above. Capture is a hard capability difference: `claude` has no `-o` flag at all, so the redirected-stdout form is forced, and it is already the delivered contract in `tasks/done/001d-codex-task-loop-peer-opinions.md:21`. Stdin is a house-style choice instead — `claude -p` accepts the prompt positionally or on stdin — and the post-014 codex-side canonical peer step has settled on the stdin form (`codex/dev-skills/skills/review-cycle/SKILL.md:110`), which also keeps the prompt literal rather than shell-interpolated. The five codex-side consumers now import that canonical step instead of carrying their former, inconsistent launch copies (`codex/dev-skills/skills/address-review/SKILL.md:253`, `codex/dev-skills/skills/address-reviews/SKILL.md:211-212`, `codex/dev-skills/skills/address-tasks/SKILL.md:162`, `codex/dev-skills/skills/address-tasks-serialized/SKILL.md:294`, `codex/dev-skills/skills/resolve-open-questions/SKILL.md:186`). Note that closing stdin outright is only the codex-provider reading of the general "stdin redirected, never left on the caller's terminal" rule, and must not be mirrored as such into a tree whose peer is Claude. Liveness is not a third independent choice but a consequence of capture: the token check works for codex only because `-o <path>` puts the path in the peer's own argv, and Claude's redirect leaves argv without it, so transcribing the codex form into the Claude tree gives a check that can never match — forfeiting a healthy peer on the first probe. `wait` is not the substitute, because a harness Bash call is a fresh shell that does not own the process; `kill -0` on the identifier established at launch is what answers the question from a later shell. The codex-side canonical step therefore warns that a plain background subshell can orphan `claude` or its descendants (`codex/dev-skills/skills/review-cycle/SKILL.md:95`), records the session leader separately from the wait supervisor (`codex/dev-skills/skills/review-cycle/SKILL.md:98-111`), forbids inferring the PGID from that supervisor (`codex/dev-skills/skills/review-cycle/SKILL.md:118`), and probes the handed-off group with `kill -0` (`codex/dev-skills/skills/review-cycle/SKILL.md:124`). Those are now canonical-step concerns rather than five per-consumer repairs: a fallback that retains the existing handoff keeps it, while a fallback written fresh may record the peer PID directly, but neither may probe or signal a supervisor PID as if it were the peer.
- Peer prompt guidance additions (apply in the canonical prose and workflow templates): forbid network access (read-only sandboxes have no GitHub egress — pass verbatim thread text/diffs instead), and require the peer to state explicitly whether it **executed** tests or judged them statically (read-only sandboxes typically cannot write build-tool caches, so "this test would fail" is usually a static claim).
- **Convert each consumer's peer-step import to the wholesale form while you are rewriting it.** All five consumers (`address-tasks`, `address-tasks-serialized`, `address-review`, `address-reviews`, `resolve-open-questions`) currently import `review-cycle`'s *The peer step* by naming its pieces — "its preflight, pinned-strength launch, outcome vocabulary, and gating are defined there" and similar. That is the closed enumeration tasks 019 and 025 replaced everywhere else with "every rule that skill states … binds here, later additions included"; the peer step is the last section still imported as a list. This task is what makes it bite: every rule it adds there — the helper's outcome mapping, its timeout and retry semantics, the strength passthrough — reaches a consumer only if someone hand-updates five enumerations to name it, and missing one leaves that consumer silently on the old contract. Rewrite each to bind the section whole, in the consumer's own mirror vocabulary; the two flavors are expected to differ in idiom and must agree on the rule.
- Concurrency for the batch skills: an **optimistic session-local adaptive throttle**, not a fixed cap. Start unbounded; when peer outcomes show trouble (`timeout`, `failed`, and `forfeited` only when its `reason` identifies empty/garbled output — sustained fan-outs of concurrent `codex exec` runs have degraded into empty final outputs), cap NEW launches at 8 (or the current in-flight count if lower — in-flight calls are never killed, they just finish), halve on each further trouble cluster, and QUEUE invocations beyond the cap rather than forfeiting them. Other `forfeited` reasons remain non-blocking outcomes and do not step the throttle down. Each halving **rounds down** to a whole number — `floor(cap / 2)`, before the floor below is applied — so from 8 the ladder reads 4 and then 2, while a first cap the in-flight count left odd steps 7 to 3 rather than to 4. State the rounding rather than the 8/4/2 ladder alone: that ladder is only the case where the first cap happened to be a power of two, and an unrounded rule lets two renderings of the same policy permit different numbers of concurrent launches. A trouble cluster is one cap generation's worth of trouble: outcomes from calls already in flight when a step-down happened belong to the cluster that caused it, so the cap halves again only on trouble from a call launched under the current cap — which keeps the unit derivable from the run's own state rather than from a wall clock the workflow rendering may not read, and stops one burst of concurrent failures from collapsing 8 to 2 as its results trickle in. **The cap never drops below the floor of 2, whichever rule produced it:** the trouble that triggers a step-down is usually a peer *finishing* badly, so when the troubled call was the only one in flight the "current in-flight count" is zero — a literal reading would cap new launches at zero, queue every subsequent peer, and leave no running call whose completion could ever raise the cap again. Clamp to `max(2, …)` so the throttle always keeps draining the queue. Auth/usage short-circuits stay classified `unavailable` (non-blocking, not throttle events). The counter is session-local with no cross-container coordination (the maintainer runs several containers concurrently, so no global measure exists), resets next session, and every step-down is surfaced in the run summary so a future learnings pass can calibrate real limits. This bullet is the ONLY statement of peer concurrency policy in this repo: it binds every rendering of the peer step — the prose skills, their Codex mirrors, and the workflow rendering — and no other task may set a cap, a floor, or a fan-out shape of its own. It supersedes in particular the fixed 2–3 cap that powbox's forfeited task 041 carried, which is not adopted. 014's workflow-rendering rules draw out what this policy implies for the workflow rendering specifically, and state no policy of their own.

## Implementation notes

- A single supervised **foreground** `peer-review-run` call is now the recommended shape (the helper owns timeout/retry/reaping), sized under the caller's tool timeout via `--timeout`; where a skill wants reviewer+peer concurrency, launching the `peer-review-run` invocation in the background and reading its single-line JSON on completion is fine — the helper's PID is safe to track.
- Choose `--artifact-root` OUTSIDE the reviewed worktree (the helper requires it) and inside session-scoped scratch space; artifact dirs are per-invocation and private.
- Keep the diff-oriented prompt guidance: the Claude provider has no shell, so prompts should embed the diff or name the base ref.
- Do not grow the skills: this change should roughly swap snippet-for-snippet plus the short fallback paragraph; resist restating the helper's internals.

## Validation

- Dry-run one `address-review` round in a powbox container against a disposable PR: peer launches via the helper, outcome JSON parses, an `unavailable` (e.g. codex logged out) round proceeds non-blocking.
