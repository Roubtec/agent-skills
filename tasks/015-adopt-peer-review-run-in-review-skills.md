# 015 — Adopt the peer-review-run contract in the review skills' peer steps

Every line-number citation in this file is as of commit `b9ace66b` (the `main` tip when task 015b was implemented); re-derive it before editing if the named construct has moved since.

## Why this task exists

The post-014 canonical peer step still documents a raw backgrounded launch (`codex exec --sandbox read-only --cd "$worktree" -o "$outfile" … &`, `plugins/dev-skills/skills/review-cycle/SKILL.md:101-103`), which `address-review`, `address-reviews`, `address-tasks`, `address-tasks-serialized`, and `resolve-open-questions` now consume by reference rather than copying. Months of field use across kalm2, jabko, Scribz, and powbox sessions show that pattern is a reliability tarpit every orchestrator re-hits:

- run through a harness Bash tool, the wrapping shell exits immediately and the completion notification describes the **launcher**, not the peer — every launch needed a `nohup … &` workaround plus a `pgrep` liveness verification round-trip;
- `pgrep -f "codex exec"` returns the entire multi-KB prompt from the process command line (34 KB in one liveness check), and `pkill -f <token>` has killed the killing shell itself when the token appeared in its own argv;
- prompts assembled in double-quoted shell variables were corrupted by backtick/`$( )` expansion;
- a single foreground call capped by the Bash tool's 10-minute maximum silently forfeited the peer opinion on exactly the largest, most security-sensitive diffs (exit 143, no output file);
- an empty `-o` file is ambiguous between "still running", "finished but forfeited", and "crashed".

powbox now bakes `peer-review-run` (`/usr/local/bin/peer-review-run`), a provider-neutral runner that owns all of this: literal prompt-file handling (stdin, never shell-interpolated), read-only provider execution with config/hook isolation, process-group supervision with timeout, transient-only retry (auth/usage short-circuits to `unavailable`), reaping on every exit path, and a machine-readable result — final stdout line is one JSON object, schema `powbox.peer-review-run/v1`: `{ schema, provider, outcome, verdict, elapsedSeconds, exitStatus, attempts, retried, liveProgress, artifactDir, reason }`, `outcome ∈ passed | issues | unavailable | timeout | forfeited | failed`, exit 0 for any produced outcome. powbox's `docs/architecture.md` explicitly names this contract as the adoption boundary for these skills. Inspection of the installed v1 contract during implementation found that this premise was incomplete: `artifactDir` names only a directory, while neither a provider-neutral review file nor the review text itself is documented. The provider-specific envelopes and private filenames beneath that directory are implementation details, not an adoption contract from which these skills can recover and relay findings verbatim.

**Delivery status:** this task deliberately lands incomplete for both provider swaps. It delivers the canonical protocol, wholesale imports, prompt/evidence guidance, adaptive throttle, and hardened raw lifecycles, but retains both raw launches until powbox supplies (1) the configured Codex model passthrough tracked in [powbox issue #145](https://github.com/Roubtec/powbox/issues/145) and (2) a documented provider-neutral `reviewFile` or `reviewText` field in the helper result. The second improvement has been requested for powbox alongside this implementation; until its pickup branch or task URL is durable, issue #145 is the stable cross-project pointer and this paragraph is the exact requested contract.

## Scope

Included:

- Prepare the canonical `review-cycle` peer step and its workflow renderings for a later `peer-review-run` swap while retaining the hardened raw provider launches until both powbox prerequisites above land. The eventual shape remains `peer-review-run --provider codex --worktree "$worktree" --prompt-file "$promptfile" --artifact-root "$artifact_root" [--timeout N]` on the Claude-led side and `--provider claude` on the Codex-led side; consumers continue to import the canonical step.
- Map the helper outcome vocabulary onto the skills' existing gate vocabulary now so the later launch substitution does not alter gate semantics: `issues`/`passed` feed the verdict logic unchanged; `unavailable`, `timeout`, `forfeited`, `failed` are the existing explicit non-blocking outcomes. Do not claim `artifactDir` identifies the full review prose. Conversion requires a documented provider-neutral `reviewFile` or `reviewText`, and the cycle must read that payload before applying verdict logic or relaying findings.
- Prove a Claude-provider verdict against the pinned OIDs and literal embedded diff evidence. Missing proof changes a `passed` result to `forfeited`, but an `issues` result keeps its outcome and findings verbatim while carrying the exact evidence-failure reason and note; an audit failure must never discard grounded review feedback.
- Keep the existing protocol semantics untouched: preflight-once, `peer-opinions=off`, grounding spot-check, blocking+minor gating, verbatim finding relay, peer never required for publication.
- **Carry the review-strength baseline across the eventual swap, and pin effort at `medium`.** `medium` is the default and encouraged reasoning effort for every peer invocation. This supersedes the `high` effort stated by archived tasks 001 and 014 while leaving the model-capability rule intact: a high-capability tier, never an economy one, named by rolling alias or harness default and never by a dated model ID. The raw paths pin everything their CLIs expose stably: the Codex peer uses `-c model_reasoning_effort=medium` and leaves its model to the configured high-capability default, while the Claude peer uses `--model opus --effort medium`. The installed helper carries effort for both providers and the `opus` model for Claude, but its Codex adapter's config isolation still loses the configured model; that prerequisite is tracked in [powbox issue #145](https://github.com/Roubtec/powbox/issues/145). Independently, schema v1 does not expose a documented provider-neutral full-review payload, so neither provider converts yet. When powbox provides both prerequisites, every helper invocation must state `--effort medium` explicitly, the Claude provider must state `--model opus`, the Codex provider must carry the configured high-capability model without a dated literal, and the result must report the effective model and effort.
- Retain and harden the **primary raw path** until both helper prerequisites land: write the prompt via quoted heredoc (`<<'PROMPT'`), launch with `nohup … &` with stdin redirected (never left on the caller's terminal) and a unique per-attempt output path, check liveness without ever matching on the prompt text, and signal the peer through the same identifier the liveness probe resolved. Record the provider PID at launch — under the direct `nohup <provider> … &` shape, `$!` becomes the provider's PID — and persist it with its `/proc/<pid>/stat` start time for later `kill -0`, TERM, and KILL checks. Never insert a wait supervisor, session leader, or process-group target around the Claude launch: a plain `nohup … &` shares the caller's group, so signalling that group could kill the caller. Use bounded TERM, then KILL only while the PID/start-time identity still matches, then prove death; a survivor stops the cycle rather than becoming a non-blocking peer outcome. Treat a non-empty result artifact containing a `VERDICT:` line as authoritative after PID death, and never run the raw peer as a capped foreground call. Provider-specific capture and stdin still differ: codex uses `-o <path>` and `< /dev/null`; Claude uses redirected stdout with a separate stderr file (`claude -p … > <stdout-file> 2> <stderr-file>`, never `2>&1`) and `< "$prompt_file"`. Once both prerequisites land, this becomes the helper-absent fallback triggered by `command -v peer-review-run` failing.
- Background for the provider-specific rules above. Capture is a hard capability difference: `claude` has no `-o` flag at all, so the redirected-stdout form is forced, and it is already the delivered contract in `tasks/done/001d-codex-task-loop-peer-opinions.md:21`. Stdin is a house-style choice instead — `claude -p` accepts the prompt positionally or on stdin — and the post-014 codex-side canonical peer step has settled on the stdin form, which also keeps the prompt literal rather than shell-interpolated. The five codex-side consumers import that canonical step instead of carrying variants. Closing stdin outright is only the codex-provider reading of the general "stdin redirected, never left on the caller's terminal" rule and must not be mirrored into the Claude tree. Claude's redirected output path never reaches its argv, which is why the fresh direct-PID handoff replaces a path-pattern probe there.
- Peer prompt guidance additions (apply in the canonical prose and workflow templates): forbid network access (read-only sandboxes have no GitHub egress — pass verbatim thread text/diffs instead), and require the peer to state explicitly whether it **executed** tests or judged them statically (read-only sandboxes typically cannot write build-tool caches, so "this test would fail" is usually a static claim).
- **Convert each consumer's peer-step import to the wholesale form while you are rewriting it.** All five consumers (`address-tasks`, `address-tasks-serialized`, `address-review`, `address-reviews`, `resolve-open-questions`) currently import `review-cycle`'s *The peer step* by naming its pieces — "its preflight, pinned-strength launch, outcome vocabulary, and gating are defined there" and similar. That is the closed enumeration tasks 019 and 025 replaced everywhere else with "every rule that skill states … binds here, later additions included"; the peer step is the last section still imported as a list. This task is what makes it bite: every rule it adds there — the helper's outcome mapping, its timeout and retry semantics, the strength passthrough — reaches a consumer only if someone hand-updates five enumerations to name it, and missing one leaves that consumer silently on the old contract. Rewrite each to bind the section whole, in the consumer's own mirror vocabulary; the two flavors are expected to differ in idiom and must agree on the rule.
- Concurrency for the batch skills: an **optimistic session-local adaptive throttle**, not a fixed cap. Start unbounded; when peer outcomes show trouble (`timeout`, `failed`, and `forfeited` only when its `reason` identifies empty/garbled output — sustained fan-outs of concurrent `codex exec` runs have degraded into empty final outputs), cap NEW launches at 8 (or the current in-flight count if lower — in-flight calls are never killed, they just finish), halve on each further trouble cluster, and QUEUE invocations beyond the cap rather than forfeiting them. Other `forfeited` reasons remain non-blocking outcomes and do not step the throttle down. Each halving **rounds down** to a whole number — `floor(cap / 2)`, before the floor below is applied — so from 8 the ladder reads 4 and then 2, while a first cap the in-flight count left odd steps 7 to 3 rather than to 4. State the rounding rather than the 8/4/2 ladder alone: that ladder is only the case where the first cap happened to be a power of two, and an unrounded rule lets two renderings of the same policy permit different numbers of concurrent launches. A trouble cluster is one cap generation's worth of trouble: outcomes from calls already in flight when a step-down happened belong to the cluster that caused it, so the cap halves again only on trouble from a call launched under the current cap — which keeps the unit derivable from the run's own state rather than from a wall clock the workflow rendering may not read, and stops one burst of concurrent failures from collapsing 8 to 2 as its results trickle in. **The cap never drops below the floor of 2, whichever rule produced it:** the trouble that triggers a step-down is usually a peer *finishing* badly, so when the troubled call was the only one in flight the "current in-flight count" is zero — a literal reading would cap new launches at zero, queue every subsequent peer, and leave no running call whose completion could ever raise the cap again. Clamp to `max(2, …)` so the throttle always keeps draining the queue. Auth/usage short-circuits stay classified `unavailable` (non-blocking, not throttle events). The counter is session-local with no cross-container coordination (the maintainer runs several containers concurrently, so no global measure exists), resets next session, and every step-down is surfaced in the run summary so a future learnings pass can calibrate real limits. This bullet is the ONLY statement of peer concurrency policy in this repo: it binds every rendering of the peer step — the prose skills, their Codex mirrors, and the workflow rendering — and no other task may set a cap, a floor, or a fan-out shape of its own. It supersedes in particular the fixed 2–3 cap that powbox's forfeited task 041 carried, which is not adopted. 014's workflow-rendering rules draw out what this policy implies for the workflow rendering specifically, and state no policy of their own.

## Implementation notes

- After both prerequisites land, a single supervised **foreground** `peer-review-run` call is the required converted shape (the helper owns timeout/retry/reaping), sized under the caller's tool timeout via `--timeout`. Until then, keep the hardened raw launch and its explicit lifecycle supervision. In either case, concurrency belongs between the Peer role/stage and Reviewer, not around a helper process.
- Choose `--artifact-root` OUTSIDE the reviewed worktree (the helper requires it) and inside session-scoped scratch space; artifact dirs are per-invocation and private.
- Keep the diff-oriented prompt guidance: the Claude provider has no shell, so prompts should embed the diff or name the base ref.
- Do not couple the skills to helper internals: the later swap consumes only documented result fields, never provider-specific envelopes or guessed filenames below `artifactDir`.

## Acceptance criteria

- Both canonical provider renderings explicitly record the two powbox prerequisites and retain their raw launches as the primary path. They do not claim that `artifactDir` identifies review prose, parse a provider-specific result envelope, or invent an artifact filename. Consumer skills import that canonical step wholesale.
- The retained raw paragraph keeps the provider-specific forms distinct: Codex result capture uses `-o` with `< /dev/null`, while Claude redirects stdout and separate stderr with `< "$prompt_file"`. The fresh Claude launch records `$!` as the direct provider PID with start-time identity, uses that positive PID alone for `kill -0`, TERM, and KILL, and stops on a survivor; it has no path-token probe, process-group/session leader, wait supervisor, or `pkill -f`. All five Codex-side consumer mirrors inherit the canonical launch rather than carrying variants. Once both prerequisites land, these same paragraphs become the `command -v peer-review-run`-missing fallbacks.
- Peer prompt templates carry the no-network and executed-vs-static-verification instructions.
- The Codex-side canonical prose rendering records that its eventual helper conversion uses `--provider claude`, but retains the hardened raw launch until the stable-review-payload prerequisite lands; consumer mirrors inherit it.
- Existing gate semantics (grounding, blocking+minor, non-blocking unavailability, `peer-opinions=off`) are textually preserved.
- Every retained raw peer step pins review strength per invocation in its provider's form — the Codex peer's effort, the Claude peer's model and effort — and a real invocation is observed running at the pinned strength, not merely instructed to. The pinned effort is `medium` everywhere. The eventual helper path must meet the same observations and expose a stable full-review payload before conversion.
- The batch skills carry the adaptive throttle as specced: unbounded start; a first step-down to `max(2, min(8, current in-flight))`; halving on each further trouble cluster — one step-down per cap generation, so only trouble from a call launched under the current cap halves it again — each halving rounding down (`floor(cap / 2)`, so an odd cap of 7 steps to 3, not 4), down to the floor of 2, which no rule may undercut; in-flight calls never killed; invocations beyond the cap queued rather than forfeited; trouble counted for `timeout`, `failed`, and `forfeited` only when its `reason` identifies empty/garbled output, with other forfeitures and auth/usage `unavailable` outcomes excluded as throttle events; the counter session-local, uncoordinated across containers, and reset next session; and every step-down surfaced in the run summary.
