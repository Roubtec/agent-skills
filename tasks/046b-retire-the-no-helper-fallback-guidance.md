# 046b — Retire the no-helper fallback prose for the disposable-clone helpers

## Why

Fourteen shipped skill files — seven under `plugins/dev-skills/skills/` and their seven `codex/dev-skills/skills/` mirrors — carried a "where the helper is absent" fallback for `dc-enter`/`dc-remove`. That prose existed once per skill and said roughly the same thing each time, and the skills are already long enough that a rule repeated fourteen times is a real cost.

Provenance was measured twice, and the second measurement is why this task shipped when it did. The table below is the current one; the row that moved is `Codex on powbox`, and what moved it was `Roubtec/powbox` task 061 landing and a rebuilt image carrying its output.

| Consumer | `dc-enter` on PATH? | Why |
|---|---|---|
| Claude on powbox | yes | Claude's plugin runtime puts `plugins/dev-skills/bin/` on PATH — *not* powbox |
| Claude off powbox | yes | the same plugin runtime, and the helpers ship in that tree |
| Codex on powbox | yes | powbox bakes both helpers into `/usr/local/bin` from this repository's `plugins/dev-skills/bin/`, through the same pipe that bakes `gh-review-threads` |
| Codex off powbox | **no** | `codex/` carries only `skills/` — no `bin/`, no install scaffolding — so the documented `install` step is what covers it |

Both measurements are recorded rather than one overwriting the other, because the first is what justified the deferral and the second is what ended it, and a reader who sees only the second cannot tell why the task was ever gated.

- **First measurement, taken while powbox task 061 was unstarted:** `/usr/local/bin/dc-enter` and `/usr/local/bin/dc-remove` did not exist on the image, while `/usr/local/bin/gh-review-threads` did and was byte-identical to this repository's copy, and `command -v dc-enter` inside a Claude container resolved under `~/.claude/plugins/cache/` rather than `/usr/local/bin`. Checked helper by helper against that image, the `dc-*` pair was the only helper this repository's own guidance names that the image did not carry. On that reading the fallback's live audience was *every* Codex session, on powbox as much as off it.
- **Second measurement, taken against the rebuilt image this task was implemented on:** `/usr/local/bin/dc-enter` and `/usr/local/bin/dc-remove` exist, are executable, and are byte-identical to this repository's `plugins/dev-skills/bin/` copies; a functional round trip passes from this checkout (a clone handed back outside `/workspace`, a ref deletion inside it leaving this repository untouched, a reused slug refused, `dc-remove` freeing it); and a clean-environment login shell resolves both through `/usr/local/bin`, which is what a `codex exec` peer gets. So the Codex flavor is covered on a current image, and the uncovered population is a Codex session off powbox or on an image built before the bake.

It was always an *install-state* difference rather than a harness-capability one, and `README.md` documents the remedy (`mkdir -p ~/.local/bin && install -m 755 plugins/dev-skills/bin/dc-enter plugins/dev-skills/bin/dc-remove ~/.local/bin/`). What changed is who has to run it: not every Codex session, only one whose image did not bake the pair.

Two facts bound what this task claims, and both were measured rather than assumed:

- **The `codex/` tree is not where this got fixed.** Powbox task 061, in the `Roubtec/powbox` repository, bakes both helpers into `/usr/local/bin` from this repository's `plugins/dev-skills/bin/` through the same pipe that already bakes `gh-review-threads`, and settles the duplication question in the same breath: a baked copy for Claude alone "would create two artifacts to keep in sync for no gain. The baked copy serves both." A copy under `codex/dev-skills/bin/` would be a third. Shipping `bin/` into `codex/` would not put it on PATH by itself either — Codex has no equivalent of Claude's plugin runtime; the tree is files in a config folder — so it would buy a self-contained tree at the price of a mirror to keep in sync, with the manual PATH step surviving either way.
- **This retirement covers the plugin-shipped helpers only.** Any helper that is baked into the powbox image rather than shipped from this repo keeps its fallback, because a container on an older image genuinely lacks them and their fallbacks stay reachable. Task 046 widened one such fallback (the Cleanup pre-removal marker list) precisely because it is reachable. Do not delete those.

`gh-review-threads` is settled and needs no drift check: powbox sources it directly from this repo and its CI smoke tests assert the script's presence.

## Scope history

The original scope was amended twice. The withdrawal below stands; the deferral below was lifted once its gate was met, and is kept as the record of why the two halves shipped together in one PR rather than in two.

**Withdrawn — original acceptance criterion 1, shipping `bin/` into `codex/`.** Do not create `codex/dev-skills/bin/`. Powbox task 061 bakes both helpers for both flavors from this repository's `plugins/dev-skills/bin/`, on the settled ground, stated there, that a baked copy for Claude alone would create "two artifacts to keep in sync for no gain" and that the one baked copy serves both flavors. A `codex/` copy would be the third artifact, and would contradict the one-source-of-truth rule that repository's architecture chapter encodes for vendored baked helpers.

**Deferred, then unblocked — the single stated precondition and the per-skill deletions.** Both were gated on a rebuilt powbox image actually carrying the helpers, not merely on powbox task 061 merging. That task's implementation notes state: "Do not add a fallback path for containers built before this lands. The consumer wording that 017 owns already degrades on `command -v`, which is the whole point of that clause." Containers built before it lands are a population that outlives its merge, which is why the gate was the image rather than the merge, and powbox 061 relied on this repository keeping the fallback until then. Landing the precondition and the deletions early would not have degraded *silently* — the precondition's whole point is that a missing helper stops rather than improvises — but it would have stopped **every** Codex session on every container whose image predated the bake, until its operator ran that install step by hand. Buying off that stop is what the gate was for. The gate is now met: powbox 061 is merged (`Roubtec/powbox` commit `13d3b83`, with `aea5463` baking the helpers and `b88e6f5` recording the placement decision), and the second measurement above is of an image that carries its output. The deferral text said the unblocked half would "land on a new branch for this task"; that assumed the ungated half had already shipped, which it had not, so both halves shipped in this task's single PR instead.

**The sweep's real surface is larger than the fourteen skill files, and a shipped suite guards it.** The same rule shipped in the dynamic workflows too, spelled "Where the helper is absent, use an absolute path outside the repository — never a relative one, and never the repository itself." — `plugins/dev-skills/workflows/wf-address-tasks.js` carried it at two sites, `wf-review-cycle.js` at two, and `wf-address-review.js` at one. Those five sites were **in** the sweep: a precondition stated once cannot coexist with a fallback the workflows still render into every subagent prompt they compose. The skill files spell the same rule slightly differently ("name an absolute path" rather than "use an absolute path"), which is why a sweep keyed on one spelling would have missed the other half.

**Two guard entries were implicated, not one.** `scripts/test-subagent-destroy-boundary.mjs`'s `REQUIRED` clause table anchored the workflow spelling as its `absolute-path fallback` entry, so deleting the clause turned that suite red by design — which is what the retained criterion that every suite in `.github/workflows/tests.yml` passes was for. But the neighbouring `disposable-clone destination` entry, a bare existence check on the literal `command -v dc-enter`, went red with it, because retiring the conditional retires the probe the entry matched. That second entry is the one the original scope did not name, and it could not simply be restored: its own commentary justified keeping it bare on the ground that "what must survive is pinned in full by the clauses either side", one of which was the fallback. So the pair was replaced by a single span running from the directive's polarity into the destination it names, and the commentary that argued for two entries was rewritten to argue for one.

## What was done

- **Ungated, delivered first:** corrected `README.md`'s `codex/` bullet, and corrected the `DC_ROOT` sentence in the `dc-enter`/`dc-remove` bullet to the resolution order the helper actually implements — an optional absolute-path override, else `$TMPDIR`, else `/tmp` — instead of predicting that powbox would set it. That prediction also ships in `plugins/dev-skills/bin/dc-enter`'s own header, in the comment block containing "`DC_ROOT` is the placement interface"; correcting a shipped helper is out of this task's scope, so task 046d carries it, and powbox's own architecture chapter now supplies the replacement fact — it sets **neither** `DC_ROOT` nor `DC_AGENT`, because both helpers' defaults already land where powbox would point them.
- **Corrected again once the gate closed:** the `codex/` bullet's claim that powbox bakes `gh-review-threads` but not the `dc-*` pair was measured-true when it landed and false after powbox 061, so it now states the bake as the observed fact it is and reserves the install step for a Codex session off powbox or on an image built before that bake. The install command and the `mkdir -p` rationale sentence are unchanged; both remain correct and load-bearing.
- **The precondition, stated once.** It lives under `README.md`'s `## Consumers` heading, in the paragraph beginning "`dc-enter` and `dc-remove` are a precondition of these skills". That section already tabulates the three consumer populations that have a distribution channel — the fourth, a Codex session off powbox or on an image built before the bake, is named in the prose rather than given a row, because the table is keyed on channel and that population has none — and the precondition is an install-state fact about how each of them gets a binary rather than a per-run decision any skill makes. Stating it in a shipped skill file would have been once per flavor at best, and `reap-tasks` reaches no shared building block, so it would have been neither once nor complete.
- **The fourteen skill sites and the five workflow sites lost the conditional and its fallback branch outright, and gained one pointer.** What remains is the unconditional `DC="$(dc-enter <slug>)"` and the guarded `cd` form task 046 added — which is what turns a missing helper into a stop rather than a degradation, since with no second destination named anywhere an empty `DC` aborts the shell before the first command that writes. Its message now carries the remedy with it: `cd -- "${DC:?dc-enter returned no path — install it from the dev-skills plugin bin/}"`. That is a pointer, not a fallback branch and not a second destination, so it reinstates nothing this task retires, and it is what makes the stop itself name the install step rather than delegating that to a file no run reads. The install *command* is still written once. The message holds no backtick and no `$`, since the word of a `${var:?word}` expansion is itself expanded.
- **The guard suite was updated in the same change**, per "Two guard entries were implicated" above.
- **A third guard entry, added in this task's review round.** That pair left the guarded `cd` itself pinned by nothing: deleting the sentence from all five boundary constants passed every suite in `.github/workflows/tests.yml` at exit 0. The commentary claiming the form was "pinned elsewhere on its own terms" by `scripts/test-address-review-reconcile.mjs` was false in the strongest direction — that file lists the `${DC:?…}` span in `KNOWN_LITERAL_SPANS`, an *exclusion* list for a scan hunting unrendered builder interpolations, so deleting the clause makes that scan pass more easily and could never fail it. With the fallback retired, the empty-`DC` abort is the only thing between a missing helper and a subagent running in the shared checkout, so `REQUIRED` gained a tenth entry pinning that sentence from its imperative verb through the install step the message names, and the false claim was corrected where it stood. The measured pinned fraction moved with it, and is now stated in aggregate rather than as a figure claimed of each constant: 66.8% over the five, 65.4% of a `CYCLE_DESTROY_BOUNDARY` and 67.8% of a `DESTROY_BOUNDARY`.
- **The same round left one hole open deliberately.** The fourteen `SKILL.md` copies of the destroy-boundary bullet are guarded by nothing at all — the prose deletion guard in that suite covers task 045's output-destination clauses only, and its census is keyed on a warning phrase those bullets do not carry, so anchoring them takes a third category rather than a row. That is pre-existing and wider than this task, so it is task 046e rather than silent scope growth here.
- No fallback for an image-baked helper was touched.

## Considered and declined

**Move the no-helper guidance into a separate file referenced only by the Codex-flavored skills.** Rejected for two reasons that stand together. The first is what this task is *for*: the end state is a single precondition, so a shared file would centralize — and thereby invest in — exactly the fallback behavior being retired, while splitting one contract across two documents for a branch already scheduled for deletion. The second is the axis. The two flavors are kept in lockstep and diverge only where *harness capabilities* differ, whereas a missing helper is an *install-state* difference; flavor is only ever a correlate of it, not its cause, and powbox task 061 broke even the correlation by giving a rebuilt image's Codex sessions the helper.

Two earlier versions of this section's reasoning are recorded rather than quietly replaced, since each was true when written and each was falsified by the next measurement. The original — "the same Codex user on powbox has the helper on PATH" — was false under the first measurement, which found no `dc-enter` on that image. Its replacement — that a Codex user on powbox has no `dc-enter` either — is false under the second, since a current image bakes it. What survives both is the axis argument above, which never depended on either reading.
