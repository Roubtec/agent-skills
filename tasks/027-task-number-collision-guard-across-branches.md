# 027 — Guard task-file numbering against same-number collisions across in-flight branches

## Why this task exists

Task numbers are allocated by scanning the working tree for the next free number, but concurrent branches each scan their **own** tree. In Scribz, PR #78 created `tasks/024-bound-the-unconfirmed-entitlement-retry-rate.md` while PR #83 already carried `tasks/024-bound-sqlcmd-execution-time-in-the-integration-rig.md`; the filenames differ, so Git reports no conflict and both would have merged, silently corrupting the numbering convention. It was caught only by an explicit manual cross-branch check. The `address-tasks` pre-PR collision guard already deconflicts **add/add clashes on identical paths**; the same-number-different-name case is invisible to it.

## Scope

Included:

- **`address-tasks` (and serialized variant) pre-PR guard extension — what is compared:** before opening a PR that adds task files, check the new files' task numbers against the comparison set defined under Implementation notes below, matching by the full number plus any letter suffix as the rule there specifies (both the set and the matching rule live there, so these two bullets describe only how the scan is carried out); a same-number hit that the identical-path add/add guard does not already cover is handled like that clash (renumber one side + re-review, or hold with an imperative name). What a member contributes to the scan follows from its **kind**, and getting this wrong is the guard's likeliest false positive. State it by kind rather than by walking the membership list, which belongs to the comparison-set bullet alone: the **base branch** contributes its whole `tasks/` tree, since every number standing in it is taken; any other **tree-bearing** member contributes only the task files it *adds* relative to **its own** base, never its whole tree; and a member that is already just a **reserved number** contributes that number directly, having no tree to read. The additions-only rule for tree-bearing members is the load-bearing one: such a member inherits all of the base's task files without claiming any of them, so a whole-tree comparison would make every open PR appear to claim every existing number, and any branch relocating a task would then collide with its own inherited copy on every open head. For the same reason the scanning branch's own removals are computed against its own base alone and never as a tree-to-tree diff against another head, which would read two heads' unrelated files as a delete/add pair and exempt precisely the cross-branch collision this guard exists to catch. Compare the branch's additions against one another too — two new files claiming one number never reach a member at all, yet they collide just the same.
- **…and how each member is read:** refresh the base ref first with an **explicit refspec** — `git fetch origin '+refs/heads/<base>:refs/remotes/origin/<base>'` — and then name it as `origin/<base>` in every command below, never as the bare local `<base>`. Both halves matter. A bare `git fetch origin <base>` only updates the remote-tracking ref when the configured refmap happens to cover it, so in a single-branch or otherwise narrowly-cloned checkout it writes `FETCH_HEAD` and nothing else; verified on git 2.47, where a `--single-branch` clone of `main` fetching `feature` leaves `origin/feature` nonexistent while the explicit refspec creates it. And the fetch never touches a local branch of that name, so a literal `<base>` reads whatever the checkout last had. Either way a stale ref silently re-creates the false positive the additions-only rule exists to prevent — against an outdated base, a member's "additions" swell to include every task file the base gained meanwhile, files that member merely inherits. Read the base itself with `git ls-tree -r --name-only origin/<base> -- tasks/`. The `-r` is load-bearing there: without it `ls-tree` reports the `tasks/done` and `tasks/deferred` subtrees as single tree objects rather than their filenames, so an archived task would hide the number it still holds and the guard would clear a second claimant of it — and archived and deferred tasks remain part of the numbering history (`tasks/AGENTS.md`), so the base read covers the whole subtree, not its top level. Enumerate open PRs with `gh pr list --state open --limit <high-enough> --json number,headRefOid,baseRefName,baseRefOid` — pin the limit (or paginate) rather than accepting the CLI's silent default of 30, or a repo with more open PRs under-scans in exactly the way this guard exists to prevent. Ask for `baseRefName` too, because each member's additions are measured against **its own** base, not the repo's default branch: `address-tasks` delivers dependent work as stacked PRs (`plugins/dev-skills/skills/address-tasks/SKILL.md:71`), so a branch stacked on a sibling inherits that sibling's task files, and diffing it against the repo base would count every inherited file as its own claim and hold a routine stacked delivery. The scanning branch is measured against its own recorded base for the same reason. Only the base-branch member is read as a whole tree. Resolve each head to an object the local repo can actually read before scanning it, fetching from the **base** repo's PR ref namespace, which covers same-repo and fork heads uniformly and needs nothing but the PR number: `git fetch origin refs/pull/<N>/head`, plus one fetch of each distinct `baseRefName` in the enumeration, using the same explicit-refspec form so a narrow clone cannot silently skip the update. Fetch those bases **unconditionally**, once per distinct name — presence is not the test, freshness is. `origin/<sibling>` is always present the moment any sibling has been fetched, so a presence check would happily diff a stacked head against a remote-tracking ref that is arbitrarily behind, and that is a partial whole-tree read producing exactly the phantom claim the bullet above argues against — realistic precisely in the `address-tasks` run this per-branch rule was written for, where siblings push while the guard runs. Ask for `baseRefOid` alongside `baseRefName` for the case where the base ref no longer resolves by name (deleted or retargeted after the PR opened): fall back to that OID, and where it too is unreachable, degrade per the note-and-proceed rule below and name the head rather than scanning it against a wrong base. The head fetch brings the head's reachable history, so the merge-base the three-dot form implies resolves without a second fetch. Then take the head's additions with the three-dot form the existing guard already uses — `git diff --no-renames --diff-filter=A --name-only origin/<its-base>...<headRefOid> -- tasks/` (`plugins/dev-skills/skills/address-tasks/SKILL.md:180-186`, which diffs each branch against `branch_bases[$branch]` for exactly the reason above, so that it "never re-lists an inherited file"). The `--no-renames` is load-bearing and is *not* inherited from that exemplar, which omits it: Git detects renames by default, so a moved or renamed task file is reported as a single `R` entry that `--diff-filter=A` excludes outright — verified on git 2.47, where archiving `tasks/024-foo.md` into `tasks/done/` yields `R100` and an empty addition list. Two things break without it. A renumbering rename (`tasks/024-foo.md` → `tasks/031-foo.md`) is a fresh claim on `031` and must be caught, yet produces no addition at all and sails through. And the removal-pairing exemption below assumes moves decompose into a delete plus an add; under rename detection they mostly do not, so relocations would clear by being invisible rather than by being exempt, and only when similarity happened to clear Git's threshold — making guard behaviour depend on how much the file changed while moving. Apply `--no-renames` to the removal side of the exemption as well, so both halves of the pairing see the same decomposition. Do **not** substitute `git ls-tree` on a head; it returns the whole tree, which is the reading the bullet above forbids. A bare `git ls-tree <headRefName>` is doubly wrong — a head that exists only as `origin/<name>`, or on a fork, does not resolve as a local ref and a normal base-repo fetch does not create it, so the guard would silently skip those PRs while claiming to scan every head. Prefer the `refs/pull/` route over reconstructing a fork's `owner/repo` for a contents-API call: a renamed fork makes that pair unreliable, and the PR ref is served by the base repo regardless.
- **`write-tasks` numbering guidance:** when allocating numbers, scan not just the working tree but also open PR heads for taken numbers, recursing the whole `tasks/` subtree on both, not just its top level (a number preserved by an archived or deferred task is still taken, and an enumerated `done/`+`deferred/` pair would silently miss any subfolder added later). Two divergences from the guard are deliberate here, and neither is an oversight to be normalized. Allocation reasons about the **numeric slot** — `001a` occupies slot `001` for the purpose of picking the next free primary — which is the opposite end of the guard's full-number matching. And allocation reads each open head as a **whole tree**, where the guard reads only its additions: an allocator must avoid every number standing on that head, inherited ones included, whereas the guard is asking the narrower question of what that head newly *claims*. Resolving those heads still needs the guard's mechanic rather than a bare branch name — the same `git fetch origin refs/pull/<N>/head` route, since a fork or origin-only head does not resolve locally. On collision risk (or when the repo has multiple task-bearing PRs in flight), prefer the next number clear of all of them and say so in the task-writing commit message.
- **`review-tasks` sweep addition:** during task cleanup cycles, flag duplicate task numbers across the whole `tasks/` subtree (including `done/` and `deferred/`, where a renumber-on-archive would break references — report, don't rename there). The sweep compares the **full** task number as the guard does (three digits plus any letter suffix, per the matching rule under Implementation notes), not the bare three-digit prefix: a prefix comparison flags every legitimate `001`/`001a`/`001b` family as a duplicate, filling the audit meant to catch real collisions with noise.

Out of scope:

- A manifest-based allocator (repo-level choice; only worth proposing if the guard proves insufficient).
- Renumbering existing duplicates in any consumer repo.

## Implementation notes

- State the matching rule precisely so the guard doesn't false-positive on legitimate `001`/`001a` families. Parse each task filename into its **full task number** — the three digits plus the optional lowercase letter suffix (`001`, `001a`, `042b`) — and its slug. Two files **collide** whenever their full task numbers are identical, whatever their slugs: the slug picks the diagnostic and the remedy, never whether the hit counts. Differing slugs are the cross-branch case this guard exists for. Identical slugs at the *same* path are the plain add/add clash the existing guard already handles, and only that case may be handed off to it. Identical slugs at *differing* paths are neither, and must not be waved through as the add/add case — `tasks/done/024-foo.md` in the base does not release `024` for a branch adding `tasks/024-foo.md`, and no identical-path guard will ever see that pair — so deconflict it exactly like the differing-slug case. The one exemption is a file the scanning branch itself moves or renames, and it is a mechanical test rather than a judgement about folders: an added file bearing full number `N` is exempt when the branch also **removes** a file bearing that same full number, both measured against the scanning branch's own base as the scan bullet above specifies, pairing each removal with at most one addition. The pairing is constrained by number and always consumes an available same-number removal — a branch that swaps two numbers between two files (`024-foo` → `025-foo` alongside `025-bar` → `024-bar`) is a legitimate renumbering in which every addition finds a same-number removal, and must clear the guard even though no pairing there continues the same task. The slug and rename heuristics only *choose among* several same-number candidates: prefer the addition whose slug matches the removal's, otherwise the closest rename match, so that a branch which both relocates `N` and separately claims `N` again leaves the *new* claimant unpaired and flagged, rather than the copy it is archiving. That ordering is load-bearing for the remedy as much as the diagnosis: renumbering the flagged side must never land on a file in `tasks/done/` or `tasks/deferred/`, which the sweep bullet above forbids renaming because it breaks references. The net claim on `N` is then unchanged — one task changed path, rather than a second claimant appearing. Stated that way it covers archiving into `tasks/done/`, deferring into `tasks/deferred/`, promoting a deferred task back into `tasks/`, and an in-place slug rename, in either direction and without enumerating them. Both halves of the test are load-bearing. Keying the exemption on the destination folder instead would clear a real collision: a branch adding `tasks/done/024-bar.md` against a base holding `tasks/024-foo.md` removes nothing and is a second claim on `024`. Dropping the pairing would clear one too: a branch that archives `024-foo` *and* adds `024-bar` makes one removal cover two additions, so only one addition is exempt and the other stands as a collision. Because removals are measured against the scanning branch's own base alone, the exemption never reaches any other member, which is the correct outcome: a number another head genuinely adds stays claimed no matter what the scanning branch removes from the base. Two files whose full task numbers differ **never** collide, even when their numeric portions match: `001` and `001a` are distinct numbers that coexist by design, as do `001a` and `001b`.
- Keep it cheap, but count the whole operation rather than the local half: one `gh pr list` at guard time, one whole-tree read of the base, one fetch per open head plus one per distinct PR base, and one addition diff per head (the merge-base is implied by the three-dot form, not a separate step). The fetches dominate; they are a cost to accept rather than one to condition away — see the unconditional rule above; degrade gracefully (note-and-proceed) when the remote is unavailable or a head cannot be resolved, since local-only runs can't see PR heads — report which heads were skipped rather than treating the scan as complete. In the same spirit, the scan is a point-in-time snapshot and the guard text should say so rather than imply otherwise: each head is read at the OID the enumeration returned, so a head that advances at any point after that enumeration — before its fetch, after it, or while this branch's own PR is being opened — can claim a number the scan never sees. Do **not** chase that window — re-reading `FETCH_HEAD` against the enumerated OID and re-querying on a mismatch only moves the race later, since a head can equally advance after the last fetch and before the PR opens, so each tightening narrows a residual it can never close. That is precisely the loop 019 item 1 names, and this guard is the case for its sanctioned exit: bound the claim. The guard's claim is that no collision existed among the heads **as enumerated**; the residual is a concurrent claim landing mid-scan; and the `review-tasks` duplicate sweep above is its backstop, which is why that sweep is part of this task rather than a nicety.
- Write the guard parallelism-ready for 033, and **define the comparison set here, once** — 033 composes this guard rather than redefining it, so a second list presenting itself as the membership rule — there or anywhere else — is a defect, not a summary. Naming members while arguing a specific scenario is fine, as is the deliberately different allocation scope in the `write-tasks` bullet above. The set is the union of two groups. **Always:** the **base branch**, and every **open PR head**. **In a pipelined run, additionally:** branches **delivered earlier in the same run**, anything **merged since the run started**, numbers **reserved** by a task that has cleared the guard but not yet finished delivering, and **currently-ready siblings** awaiting the guard. First claimant wins; the second claimant renumbers, and it is never the delivered or reserved side.

## Acceptance criteria

- The batch skills' guard section names both the same-number-different-name case and the same-number-same-slug-at-a-different-path case (an archived or deferred copy still holding the number), gives them the one shared deconfliction procedure, and states the relocation exemption as a removal-pairing test rather than a list of folders, so a branch that archives, defers, un-defers, or renames one of its own tasks does not trip over its own move while a genuine second claimant still does. It also carries the remedy constraint: the renumber lands on the flagged new claimant and never on a copy in `tasks/done/` or `tasks/deferred/`, whose number the sweep bullet forbids rewriting because references break.
- `write-tasks` instructs checking open PR heads as well as the working tree before allocating, recursing the whole `tasks/` subtree on both, resolves those heads through the same `refs/pull/<N>/head` route the guard uses rather than a bare branch name that skips fork and origin-only heads, and says why both of its divergences from the guard — numeric slots rather than full numbers, whole-tree rather than additions — are deliberate.
- `review-tasks` flags duplicate full task numbers across the whole subtree, with the report-don't-rename exception for archived folders.
- The matching rule distinguishes suffix families from true collisions: it compares full number+suffix, so `001`/`001a` never trip it, while `024`/`024` always does — whether the slugs differ or match across `tasks/` and `tasks/done/` — except where the branch also removes a file of that number from its own base, one removal exempting at most one addition, with the pairing constrained by number so that a two-file number swap clears and only the slug/rename heuristic chooses among several same-number candidates. Two additions of one number on the scanning branch itself trip it as well.
- The delivered guard text carries **every** member of the comparison set as defined under Implementation notes — both of its groups, checked against that definition rather than against a list restated here, since a competing enumeration is the defect that definition exists to prevent. A guard naming only the always-members and dropping the pipelined ones fails this criterion. It also states what a member contributes by **kind** rather than by re-walking that list — whole `tasks/` tree for the base, additions relative to its own base for any other tree-bearing member, the number itself for a member that is already just a reserved number — since a whole-tree reading of a head is what turns the exemption into a blocked hygiene PR, and a second enumeration is the partial restatement this task forbids.
- `write-tasks` records a deliberately skipped number in the task-writing commit message when it clears a collision risk, so the next allocator can see the gap was intentional.
- The guard refreshes the base branch with an explicit `+refs/heads/<base>:refs/remotes/origin/<base>` refspec and then reads it as `origin/<base>` rather than a bare branch name, refreshes every distinct PR base the same way and unconditionally rather than only when absent, before computing any diff against it, resolves every open PR head to a readable object via the base repo's `refs/pull/<N>/head` rather than assuming a local ref, enumerates open PRs without relying on a default result cap, takes each head's contribution as an addition diff against **that head's own** base rather than a tree listing or a diff against the repo default, disables rename detection on both the addition and removal diffs so a moved or renumbered file cannot vanish into an `R` entry, recurses the whole `tasks/` subtree wherever it does read a tree rather than stopping at its top level, falls back to a PR's `baseRefOid` where its `baseRefName` no longer resolves and only then degrades, and names any head it could not scan instead of silently omitting it.
- The guard text states its own residual — that the scan is a snapshot of the heads as enumerated, that a head advancing at any point after that enumeration — including after its own fetch, and while this branch's own PR is being opened — can still land a duplicate, so a text describing the window as closing when the scan ends fails this criterion, and that the `review-tasks` sweep is the backstop — rather than presenting the guard as a total guarantee or adding re-query mechanics that would only relocate the race.

## Validation

- Walk the Scribz `024` scenario against the new text: both the writing skill (allocation) and the batch skill (pre-PR guard) now catch it at different stages.
- Walk the exemption in both directions, since its failure mode is a false positive that would block routine hygiene PRs rather than a missed collision. A branch that only moves one task — archiving `tasks/NNN-slug.md` into `tasks/done/`, deferring it, promoting it back into `tasks/`, or renaming its slug in place — must clear the guard silently. A branch adding `tasks/NNN-other.md` against a base holding `tasks/done/NNN-slug.md`, and a branch that archives `NNN` while also adding a second file numbered `NNN`, must both trip it.

## Review plan

Reviewer verifies the matching rule against the house numbering convention (odd primaries, even inserts, letter suffixes) and that remote-unavailable degradation is note-and-proceed, not silent skip. Reviewer also checks the relocation exemption is implemented as the removal-pairing test rather than a destination-folder heuristic, and confirms it is scoped per comparison-set member so a removal against the base cannot release a number another open PR head still claims.
