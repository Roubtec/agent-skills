# Claude Dynamic Workflows

These are Claude-only dynamic-workflow counterparts to selected development skills: deterministic JavaScript orchestration scripts that spawn and sequence agents while leaving judgment and side effects to those agents. Codex has no workflow runtime, so this directory has no Codex sibling.

The workflows are distributed by the `dev-skills` plugin and register in its namespace: invoke `/dev-skills:wf-address-review`, `/dev-skills:wf-address-tasks`, or `/dev-skills:wf-review-cycle`.

Task 014 replaced the imported workflows' inlined review loops with the shared `wf-review-cycle` and normalized the legacy unnamespaced invocation references their comments carried from the powbox import; the plugin-namespaced commands above are the invocation guidance.

## Availability

These runtime facts were verified on 2026-06-10 against the documentation and Claude Code 2.1.170:

- Dynamic workflows require Claude Code 2.1.154 or newer and a paid Claude plan or supported API provider.
- Pro accounts default workflows off; enable them with the Dynamic workflows row in `/config`, which writes `"enableWorkflows": true` to `~/.claude/settings.json`. The explicit off switches are `"disableWorkflows": true` and `CLAUDE_CODE_DISABLE_WORKFLOWS=1`.
- Claude Code caches the effective plan in `~/.claude/.credentials.json`; re-login refreshes a stale `subscriptionType`, while an explicit `enableWorkflows` setting avoids relying on that default.

## Authoring constraints

- `export const meta = {...}` must be the script's first statement. The runtime registers the command only after parsing that pure literal, whose required fields are `name` and `description`; optional fields include `title`, `whenToUse`, and `phases`.
- Scripts must be deterministic plain JavaScript. `Date.now()`, `Math.random()`, and argument-less `new Date()` are rejected because they break resume, and TypeScript syntax does not parse.
- Workflow scripts own control flow; spawned agents own repository, shell, and Git work. A blocker is returned instead of prompting for input mid-run.

## Worktree model

The runtime's `agent(..., { isolation: "worktree" })` creates a separate temporary worktree for each agent from the repository's default branch, at a runtime-chosen location with no documented redirection option. That would hide an implementer's commits from its reviewer and cannot preserve one stable task worktree across stages.

`wf-address-tasks.js` therefore uses one explicit worktree per task and reuses it for the implementer, reviewer, and later fix rounds. Independent tasks still run concurrently, while sharing the on-disk task worktree makes commits visible across stages. The workflow depends on the environment-provided `wt-bootstrap`, `wt-enter`, and `wt-remove` helpers and reports a blocker when they are unavailable.

`wf-address-review.js` is a single-PR sequential pipeline, so its agents deliberately share the current checkout rather than creating worktrees. It does not own that checkout either — its gather brief forbids switching branches, because the workflow supports a local off-shoot of a merge-pending PR, where the checked-out branch legitimately differs from the PR's head ref. The one exception is the branch reconciliation of task 021b: a run whose checked-out branch IS the PR's head ref works on it as it stands when it already carries everything the PR head has, fast-forwards it when it is strictly behind, and stops the run on any other state. That reconciliation is gated on the two names matching, so the off-shoot case never reaches it — there, "behind the PR head" is the normal state rather than the hazard.

The shared-filesystem assumption was verified on 2026-06-10 with Claude Code 2.1.170: a separately spawned agent could find the first agent's worktree, file, and commit, and a two-task workflow run kept each reviewer on its implementer's task worktree.

## Current scope

`wf-review-cycle.js` is the canonical review cycle for workflows: fixer -> fresh-eyes reviewer -> best-effort cross-harness codex peer -> fix, with explicit finding dispositions, escalated open questions in a pinned wire format, and the canonical round cap. Its cycle logic sits in a marked embeddable section (`review-cycle-core`) with two documented consumption modes — nesting via `workflow("wf-review-cycle", ...)`, and synthesis of the marked section into a flat consumer script.

`wf-address-tasks.js` expresses dependency waves, storage-aware throttling, sibling collision handling, and per-task PR creation, running each task through an embedded copy of `review-cycle-core` (embedded rather than nested so the fan-out owner makes every peer launch in its own flat state — where task 015's throttle will live — and hands every per-task cycle one shared batch-wide peer preflight/availability state). It does not build the post-batch local review stack produced by the `address-tasks` skill.

`wf-address-review.js` nests `wf-review-cycle` for its verify loop and conditionally publishes based on its flags. With no mid-run input, it behaves like the skill's hands-off mode: agents decide low-stakes ambiguity and report high-stakes blockers.

`rebase-stack` remains a skill because its value is sequential conflict judgment and user confirmation rather than agent fan-out.

## Validation

Parse-check the shipped workflow sources — `plugins/dev-skills/workflows/wf-review-cycle.js`, `wf-address-review.js`, and `wf-address-tasks.js` — with powbox's `wf-check` where it has landed: it is built against the runtime's own loading, which nothing in this repo can speak for. It is not on PATH in this repo's powbox image (checked 2026-08-05), so until it lands, stand in for it with a hand-rolled wrapper — from the repository root, once per file:

```
D="$(mktemp -d "${TMPDIR:-/tmp}/wf-check.XXXXXX")" \
  && sed '1,/^export const meta/s/^export const meta/const meta/' <file> > "$D/body.js" \
  && { echo '(async function(args, agent, phase, workflow, parallel, pipeline, log){"use strict";'; cat "$D/body.js"; echo '});'; } > "$D/w.cjs" \
  && node --check "$D/w.cjs" && rm -rf "$D"
```

Do NOT substitute a bare `node --check <file>`: the first statement in these sources is `export const meta`, and Node's module-syntax detection swallows every parse error after that token, so a bare check can fail only on an error ahead of it, up in the header comment.

The two moves the parse turns on: `export const meta` becomes a plain `const`, so the file is no longer module syntax, and the `async` function body makes the top-level `await` these scripts use legal — not their top-level `return`, which the CommonJS parse the `.cjs` extension selects admits anyway. `sed` writes to a file rather than piping into the brace group so its own exit status gates the chain — piped, an unreadable `<file>` is masked, because the shell reports the pipeline's *last* status and the brace group wraps empty input happily. `"use strict";` is ours, not an observed runtime property: it only ever rejects more, and a module-loading runtime parses strictly anyway. `mktemp -d` keeps concurrent checks apart (`wf-address-tasks` fans out task worktrees whose agents may each run one, the rule in `wf-review-cycle.js`'s artifact-directory instruction), and a failing run leaves the directory behind: a parse error's line numbers refer to the wrapped file, and an empty `body.js` with no `w.cjs` means `sed` never read the source.

These behaviors were verified on 2026-08-05 with GNU sed 4.9 and Node v24.18.1, under both `bash` and `dash`:

- Exit 0 on each of the three sources, run from the repository root.
- Exit 2 — `sed`'s own status, before `node` runs — from a wrong cwd or a typo'd path.
- Exit 1 on all three with `let OBVIOUSLY_BROKEN = ;` appended.
- A bare `node --check` exits 0 on all three both unchanged and with that same error appended, and fails only when the error is placed before the `export`.
- Both halves of the wrapper are load-bearing: without the `sed`, all three fail with `SyntaxError: Unexpected token 'export'`; without the function body, or with a non-`async` one, all three fail with `SyntaxError: await is only valid in async functions and the top level bodies of modules`. Neither half is what admits their top-level `return` — `printf 'return 1;\n' > r.cjs && node --check r.cjs` exits 0.
- A parameter name colliding with a top-level `const`, `let`, or `class` is itself a parse error — `(async function(args, agent, meta, log){"use strict"; const meta = 1; });` → `SyntaxError: Identifier 'meta' has already been declared` — and after the `sed` all three sources declare exactly such a top-level `const meta`.

A pass is not a promise that the runtime will accept the file: this wrapper stands in for the runtime's wrapping rather than reproducing it. The real parameter list is not derivable here, and by the last measurement that guess is not neutral — a real list containing `meta` would reject what this stand-in accepts. Nothing past parsing is covered either (the `meta`-literal and determinism rules under *Authoring constraints*), so a pass means only that the source is syntactically valid in a shape that admits its top-level `await`.

Check the embedded `review-cycle-core` section for byte-identity after changing it in either file. `wf-address-tasks.js` carries a copy of `wf-review-cycle.js`'s marked section, and the copy is maintained by hand — from the repository root, under `bash` (the process substitutions are not POSIX `sh`):

```
A=$(awk '/BEGIN EMBEDDABLE SECTION: review-cycle-core/,/END EMBEDDABLE SECTION: review-cycle-core/' plugins/dev-skills/workflows/wf-review-cycle.js) \
  && B=$(awk '/BEGIN EMBEDDABLE SECTION: review-cycle-core/,/END EMBEDDABLE SECTION: review-cycle-core/' plugins/dev-skills/workflows/wf-address-tasks.js) \
  && { [ -n "$A" ] && [ -n "$B" ] || { echo 'MARKERS MISSING — one or both extractions are empty'; false; }; } \
  && diff <(printf '%s\n' "$A") <(printf '%s\n' "$B")
```

Empty output — the whole chain exiting 0 — establishes that the two sections are byte-identical, marker lines included, so an edit to one was carried to the other rather than left behind in the file it was made in. The emptiness gate is why the chain is longer than a bare `diff` of the two `awk` extractions: with both marker ranges missing or renamed, both extractions are empty, `diff` compares nothing and exits 0, so the bare form's pass is vacuous exactly when the section has been lost. The gate turns that case into `MARKERS MISSING` and a non-zero status.

It establishes nothing past that: byte-identity proves the text was *copied*, not that it renders. A section whose prompts lost the destroy boundary is identically wrong in both files and passes this check unmoved, which is what the rendering suite below is for.

Run `node scripts/test-checkout-cleanliness-report.mjs` for the focused regression suite covering `wf-address-tasks.js`'s `mainCheckoutSummary` function. The test extracts that function from the shipped workflow rather than maintaining a second copy.

Run `node scripts/test-storage-probe-target.mjs` after changing where `wf-address-tasks.js` points its `df` probes or what it does with a reading. It extracts `validateBootstrapWtBase` and `nextAvailBytes` from the shipped workflow the same way — no second copy — and drives them directly: a bootstrap that reports `ok` without an absolute `wtBase` must fail the batch before any task work, and a later probe that returned nothing, could not measure, or answered with a non-positive or non-numeric value must keep the previous reading rather than widen or disable the cap. Two properties live at the call sites rather than in either function, so the suite asserts them against the source: every `storageProbePrompt(...)` call is handed the validated base — no `||` fallback, no relative `.worktrees` literal, which is the defect the suite exists for — and the gate stands between the bootstrap agent and the resolve phase, an ordering that would otherwise pass vacuously when the gate is missing entirely.

Run `node scripts/test-collision-dispatch.mjs` after changing `wf-address-tasks.js`'s `settleWaveCollisions` — the stage that turns one wave's held branches into deliveries and holds once the collision resolver has returned. It evaluates the shipped file's declaration prefix with the injected globals stubbed, the way the destroy-boundary suite does, and drives scripted resolver / re-scan / re-review packets through the actual function, so what it exercises is the dispatch rather than a second copy of it. The property it pins: the resolver's packet is hold-only evidence, and delivery is decided against the refs. A second read-only scan decides whether a clash is gone, never the resolver's own report, because a rename can be reported and only partly applied — so a claimed rename the tree does not carry holds both sides, the untouched one included. The packet's remaining jobs are both holds: an absent one — or an empty one, which is the same answer and is scripted beside it rather than left to differ by an accident of JS truthiness — holds every branch, and a `blocked` entry holds the branches its collision covers, that refusal being the one judgment no scan can re-derive. Nothing in the packet releases a branch or excuses one from the fresh delivery-tier re-review that every held branch of a cleared clash gets: "which branches did you touch" is a self-report this stage cannot check, and a resolver that edited two branches and named one would otherwise deliver the omitted branch's post-cycle edits unreviewed. The suite covers every degraded path (no resolution packet, an unusable re-scan — returning nothing, throwing, or attributing a clash to fewer than two of the held branches — the last matching `COLLISION_SCHEMA`'s own "two or more branches" contract, since a lone name leaves every branch it omits reading as cleared, each of which would otherwise read as proof the clash is gone — fewer than two of a clash's branches in hand to compare with, a clash the re-scan still names, a failed or empty-diff re-review), 027's rule that a clash is settled only when at most one branch still carries the value — re-derived by the scan rather than computed from the packet — and the cost on both sides: a wave that held nothing spawns no agent here, and the widened re-review covers the branches that deliver rather than every branch the wave held. Because the dispatch is a function this suite calls directly, it also asserts the batch body still calls it: a stage nothing invokes would pass every scenario.

The suite also covers the deviation state that crosses this stage, which task 025b added: the branch's standing deviations from LOCKED decisions are handed to the re-review — the only pass that ever sees the post-rename tree, where a deviation's text naming a renamed file or symbol has gone stale — and the assessments that come back replace the ones the cycle formed before the rename, which is what `prPrompt` leads the PR body with. The gate is the one `cycleReviewPrompt`'s deviations block already states: a standing deviation the re-review leaves unassessed HOLDS the branch, naming the unassessed texts in the hold — which carries that same pass's usable assessments too, never the pre-rename ones, because the batch Summary flattens every result's assessments (held records included) into the one list the maintainer reads, and a hold shipping an obsolete RATIFY for the deviation it just called unassessed would contradict itself there. That way round because the block is rendered from inside the mirrored section and cannot be edited from the dispatch, so a path that showed it and delivered anyway would be prose outrunning enforcement. The replacement rides the FAILED re-review the same way, and there it clears: a pass that did not pass supplies no assessments — `runReviewCycle` records the reviewer's half on a passing round alone — so that hold carries the deviation standing and unjudged rather than a pre-rename verdict this stage cannot establish still describes the branch: which branch the resolver renamed is not a claim it can check, so every branch of a cleared clash is treated as changed — the same conservative bias that widened the re-review to all of them. The hold arms *before* the re-scan clears a clash keep what they carried, no post-rename tree having been established for them. Both directions are pinned: every unusable answer shape holds — no entry, an entry for another deviation, a missing in-spec route, a hedged or refusing recommendation — while a branch with no standing deviations renders no block, is asked for nothing, and delivers (or holds) with whatever it carried untouched.

Run `node scripts/test-subagent-destroy-boundary.mjs` after changing any prompt these workflows compose. It evaluates each shipped file's declaration prefix — "each" literally, because the cut markers that drive the run are a hand-maintained map and the `wf-*.js` files present in this directory are asserted to equal its keys, so a newly added workflow fails the suite until it is given a marker, exactly as a new builder fails until it is given a fixture — and renders every builder reached from an `agent()` call site, then asks two separate questions — the boundary lives in shared constants and in a section one workflow embeds byte-for-byte, so the sources read as covered long before every prompt carries it. **Presence** is checked per rendered brief, by exact string containment: every boundary use in these sources is a bare `${CONSTANT}` interpolation, so each brief must carry one of the constants declared in its own file verbatim, and nothing is re-derived from prose. **Content** is checked once per boundary constant — the eleven clauses the boundary states, each matched by the phrase that carries it rather than by byte comparison, so a lost clause fails while wording those phrases leave open changes freely — the tolerance is per clause and bounded by its phrase rather than general, and a rewording that moves the phrase itself reads here as a loss; the directive clause's window is deliberately the narrowest of them, because a wildcard wide enough to span its verb once admitted a *negated* boundary; the constants are evaluated out of the same declaration prefix, so this is the text the briefs actually interpolate. The set of paths is discovered from the sources — with any whitespace before the paren, so `agent (fn(...))` is rendered rather than silently skipped — and every literal `agent(` occurrence is accounted for, so an *unspaced* call shape the discovery does not recognize fails the suite instead of passing as nothing to render. Two shapes it cannot see, both named in the script's header: a new branch inside a builder it already renders — widen that builder's fixtures when one is added — and a spaced call over a variable, `agent (p, ...)`, which the literal accounting pattern skips over the space. It also asserts the three out-of-section `DESTROY_BOUNDARY` constants are byte-identical, the property the comments beside them claim; the two in-section `CYCLE_DESTROY_BOUNDARY` copies ride the `review-cycle-core` byte-identity check instead. The finish-in-turn rule is checked the same way and for the same reason — a workflow that briefs deputies of its own outside the cycle declares `DEPUTY_FINISH_IN_TURN` for them, because out-of-section code does not reach into the mirrored section, and every such copy must match `wf-review-cycle.js`'s `CYCLE_FINISH_IN_TURN` exactly; a file that declares no deputy copy simply has no deputies, unless its prompts interpolate `${DEPUTY_FINISH_IN_TURN}` anyway — a declaration was owed there and the check could not read it, which fails rather than reading as "no deputies".

Run `node scripts/test-review-cycle-retirement.mjs` for the behavior suite covering every claim a pass can make about what the maintainer still has to decide — retiring an open question, dropping a locked-decision deviation, or first stating one on the way out — and the two gates that let a cycle conclude without a fresh reviewer seeing the final content. One rule runs under all of them, and is what the suite exists to hold: a claim no round accepted does not take effect. It evaluates the shipped `review-cycle-core` section of BOTH workflow files with the injected globals stubbed and scripted fixer/reviewer packets driven through `runReviewCycle`, so the embedded copy is exercised as running code rather than only as identical bytes. Byte-identity is still the contract the section is mirrored under; this suite does not replace the `awk`/`diff` check above.

It also covers the packet hard-check's measuring half, which task 025a added: a pass's `clean` is its own word about its own worktree — and the failure the check exists to contain, a packet returned mid-rebase or mid-cherry-pick, prints empty porcelain — so the cycle takes its own reading, `git status --porcelain` plus the operation-state markers, through a low-effort read-only turn told nothing about the pass it judges, and refuses the packet when that reading disagrees or cannot be taken at all. The reading is taken when the packet RETURNS rather than folded into the next reviewer round, because three of the four conclusions have no reviewer round after the pass they conclude on — the final confirmation pass first among them — so a reviewer-borne reading would leave every one of them unmeasured, and on the rounds it did cover it would arrive only once the reviewer and peer had already been spent on a worktree nobody could trust. Both directions are pinned, on both legs: a measured-dirty or mid-operation packet is refused with the failing condition named (the mid-operation case on the final confirmation pass, whose porcelain is empty), a reading that could not be taken is refused as unknown rather than passing as clean, and a measured-clean cycle concludes exactly as before, carrying one `packetChecks` entry per adopted pass on every exit including the stopped ones.

The measurer's brief is pinned not to forbid the reading it is sent to take: a rebase and a bisect leave HEAD detached, so `git branch --show-current` prints empty, and the branch assertion every other role's worktree contract carries would order the measurer to stop in exactly the states the step exists to find. The section drops that assertion for this role, and the suite checks both halves — the rendered brief on both legs, and, once and outside the section, `wf-address-tasks.js`'s own per-role contracts, since a consumer with a worktree lifecycle supplies its own text and never reaches the section's default. On that leg `wt-enter` asserts the branch itself and refuses a worktree whose HEAD is off it, so the measurer's contract reads that refusal as evidence rather than as a stop.

Run `node scripts/test-address-review-reconcile.mjs` after changing `wf-address-review.js`'s branch reconciliation — the gate that decides, before anything is addressed, whether the run may act on the checked-out branch at all. Like the suites above it evaluates the shipped source with the injected globals stubbed, driving scripted gather packets through the actual script rather than a second copy of the gate, and reads what the run returns; reaching the nested review cycle is how it observes that a run was let through. Three properties hold that gate up and each is a separate way to lose it: the off-shoot exemption is keyed on the two BRANCH NAMES, so a run on a local off-shoot proceeds whatever the gather reported (keyed on the outcome instead, a same-branch run whose agent misreports `not-applicable` would bypass reconciliation); a run on the PR's own branch continues on `work` and `fast-forwarded` and fails closed on everything else, including an outcome string the script does not know, an empty one and an absent report; and the gate sits ahead of the empty-`items` no-op, because the rule's third outcome returns no items by contract and would otherwise be reported as "nothing to address". The RULE those outcomes come from is the gather brief's, which no scenario reaches because the gather agent is stubbed with a packet already written — so it is read out of the rendered brief instead: both probes, the head they compare against (taken from what the fetch brought, since the recorded OID is normally reachable from the checkout and so survives an existence test that a moved head should fail), the off-shoot skip that reports `not-applicable`, and the outcome vocabulary, whose agreement with the strings the gate keys on is the coupling nothing else pins (rename one on either side alone and both halves stay internally consistent while every same-branch run stops). The publication guard rides along, checked in the rendered publish brief for the same reason — it is prose rather than script logic: the proper-ancestor stop must be stated ahead of the lease it would otherwise match.

Run `node scripts/test-unreviewed-close-carriage.mjs` after changing what these workflows do with a cycle that concluded without a fresh reviewer seeing the final content.
