# Claude Dynamic Workflows

These are Claude-only dynamic-workflow counterparts to selected development skills: deterministic JavaScript orchestration scripts that spawn and sequence agents while leaving judgment and side effects to those agents. Codex has no workflow runtime, so this directory has no Codex sibling.

The workflows are distributed by the `dev-skills` plugin and register in its namespace: invoke `/dev-skills:wf-address-review`, `/dev-skills:wf-address-tasks`, or `/dev-skills:wf-review-cycle`.

Task 014 replaced the imported workflows' inlined review loops with the shared `wf-review-cycle` and normalized the legacy unnamespaced invocation references their comments carried from the powbox import; the plugin-namespaced commands above are the invocation guidance.

## Availability

These runtime facts were verified on 2026-06-10 against the documentation and Claude Code 2.1.170:

- Dynamic workflows require Claude Code 2.1.154 or newer and a paid Claude plan or supported API provider.
- Pro accounts default workflows off; enable them with the Dynamic workflows row in `/config`, which writes `"enableWorkflows": true` to `~/.claude/settings.json`. The explicit off switches are `"disableWorkflows": true` and `CLAUDE_CODE_DISABLE_WORKFLOWS=1`.
- Claude Code caches the effective plan in `~/.claude/.credentials.json`; re-login refreshes a stale `subscriptionType`, while an explicit `enableWorkflows` setting avoids relying on that default.

## Authoring constraints

- `export const meta = {...}` must be the script's first statement. The runtime registers the command only after parsing that pure literal, whose required fields are `name` and `description`; optional fields include `title`, `whenToUse`, and `phases`.
- Scripts must be deterministic plain JavaScript. `Date.now()`, `Math.random()`, and argument-less `new Date()` are rejected because they break resume, and TypeScript syntax does not parse.
- Workflow scripts own control flow; spawned agents own repository, shell, and Git work. A blocker is returned instead of prompting for input mid-run.

## Worktree model

The runtime's `agent(..., { isolation: "worktree" })` creates a separate temporary worktree for each agent from the repository's default branch, at a runtime-chosen location with no documented redirection option. That would hide an implementer's commits from its reviewer and cannot preserve one stable task worktree across stages.

`wf-address-tasks.js` therefore uses one explicit worktree per task and reuses it for the implementer, reviewer, and later fix rounds. Independent tasks still run concurrently, while sharing the on-disk task worktree makes commits visible across stages. The workflow depends on the environment-provided `wt-bootstrap`, `wt-enter`, and `wt-remove` helpers and reports a blocker when they are unavailable.

`wf-address-review.js` is a single-PR sequential pipeline, so its agents deliberately share ONE location rather than each getting a runtime worktree — but which location is picked per run rather than fixed (task 018). Its gather brief works inline in the current checkout when that checkout already stands on the PR's head ref, when the run passed `inline`, or when the run passed `off-shoot` to say the checkout stands on a local off-shoot of that branch and the work belongs there; from any other branch, and from a detached HEAD, it attaches the head ref in an explicit `.worktrees/$CONTAINER_NAME/pr-<N>` worktree and reports the absolute path, which the nested cycle and the publisher are then pointed at. The off-shoot is the one case a token has to state: no test on the branch's shape can tell an off-shoot cut before the PR head from a stacked child cut from it, so without the token every branch that is not the head ref takes the worktree. A hands-off flow has nobody to ask before taking over the maintainer's checkout, which is why the worktree is the default rather than the exception, and why nothing after setup requires that checkout to be clean or leaves it moved. The path rides in the packet's `pr` object, so every result echoing it names a worktree a halted run left standing; a run that finished gives it back through the reclaim step, which refuses rather than forces on a tree still holding anything.

The branch reconciliation of task 021b runs in whichever location was picked: a run whose working branch IS the PR's head ref works on it as it stands when it already carries everything the PR head has, fast-forwards it when it is strictly behind, and stops the run on any other state. That reconciliation is gated on the two names matching, so the off-shoot case never reaches it — there, "behind the PR head" is the normal state rather than the hazard.

The shared-filesystem assumption was verified on 2026-06-10 with Claude Code 2.1.170: a separately spawned agent could find the first agent's worktree, file, and commit, and a two-task workflow run kept each reviewer on its implementer's task worktree.

## Current scope

`wf-review-cycle.js` is the canonical review cycle for workflows: fixer -> fresh-eyes reviewer -> best-effort cross-harness codex peer -> fix, with explicit finding dispositions, escalated open questions in a pinned wire format, and the canonical round cap. Its cycle logic sits in a marked embeddable section (`review-cycle-core`) with two documented consumption modes — nesting via `workflow("wf-review-cycle", ...)`, and synthesis of the marked section into a flat consumer script.

`wf-address-tasks.js` expresses dependency waves, storage-aware throttling, sibling collision handling, and per-task PR creation, running each task through an embedded copy of `review-cycle-core` (embedded rather than nested so the fan-out owner makes every peer launch in its own flat state — where task 015's throttle will live — and hands every per-task cycle one shared batch-wide peer preflight/availability state). It does not build the post-batch local review stack produced by the `address-tasks` skill.

`wf-address-review.js` nests `wf-review-cycle` for its verify loop and conditionally publishes based on its flags. With no mid-run input, it behaves like the skill's hands-off mode: agents decide low-stakes ambiguity and report high-stakes blockers.

It also rebases by default, at two delegated points — before the fixing and again once the fixes are committed (`no-rebase` suppresses both) — each its own subagent under the `review-cycle` skill's "The delegated rebase step", rendered once by `rebasePrompt` and shared by both call sites. Unlike the prose skills, neither point is skippable by judgment here: a no-op rebase is cheaper and more deterministic than deciding it would be one. A point that reports a no-op is taken at that word only where the two tips it names are equal, because the no-op claim is what switches off both the post-rebase validation and the pre-push re-verification. The commit each point pins becomes the run's review base, because every range delegated afterwards is taken against it and a remote-tracking name moves under a sibling push; the script therefore rejects anything but a full commit OID, an abbreviation included — a short id is a prefix a growing repository can make ambiguous. `no-rebase` has no rebase report to pin from and so pins the commit the gather resolved this run's target to — the target an explicit `rebase on top of <target>` named, resolved where it was named, else the PR's base ref — rather than delegating the name: dropping the rebase never drops the target, and the review base is a commit on every path. Where the pre-push point replays something, the passing verdict no longer describes the tree being pushed, so the cycle runs again over the rebased tree as a re-verification rather than a re-triage — carrying the dispositions that passed in verbatim (as the set to carry forward, and as the baseline its reviewer compares against), bounded by what is LEFT of the cycle's 12-round total (of which a re-verification may take at most four, since it fixes replay fallout rather than doing fresh work) — so the two cycles cannot together spend more reviewer rounds than a cap an invoker may lower and never raise, and a first cycle that consumed the whole budget stops the run unpublished rather than being granted more — and merged back with the superseded cycle's open questions, deviations and round count so nothing that is the maintainer's vanishes with it. That is the ordering the skill states as "before the final reviewer round", which cannot be had literally where the rounds live inside a nested cycle — and it delivers the skill's acceptance condition that the verdict authorizing the push describes the exact tree being pushed, but not its stronger one that no such verdict is rendered on a tree whose last base refresh predates its last fix: the re-verification's own fixes postdate the replay it verifies, and closing that would mean looping the rebase point and the re-verification until the last base refresh postdates the last fix — reachable, and what one re-verification that commits no fixes leaves behind, but no bounded round budget can promise reaching it inside the budget, a base that keeps moving and each replay drawing another fix costing a re-verification per pass until the run stops unpublished. The pipeline runs the pair exactly once, so the residual is that one cycle wide.

`rebase-stack` remains a skill because its value is sequential conflict judgment and user confirmation rather than agent fan-out.

## Validation

Parse-check the shipped workflow sources — `plugins/dev-skills/workflows/wf-review-cycle.js`, `wf-address-review.js`, and `wf-address-tasks.js` — with powbox's `wf-check`, which is normally on PATH: it is built against the runtime's own loading, which nothing in this repo can speak for, so it is the check to run whenever `command -v wf-check` finds it. It is baked into the powbox image rather than shipped from here, so skills refreshed into a container running an older image can still find it absent; only then, stand in for it with the hand-rolled wrapper below — from the repository root, once per file:

```
D="$(mktemp -d "${TMPDIR:-/tmp}/wf-check.XXXXXX")" \
  && sed '1,/^export const meta/s/^export const meta/const meta/' <file> > "$D/body.js" \
  && { echo '(async function(args, agent, phase, workflow, parallel, pipeline, log){"use strict";'; cat "$D/body.js"; echo '});'; } > "$D/w.cjs" \
  && node --check "$D/w.cjs" && rm -rf "$D"
```

Do NOT substitute a bare `node --check <file>`: the first statement in these sources is `export const meta`, and Node's module-syntax detection swallows every parse error after that token, so a bare check can fail only on an error ahead of it, up in the header comment.

The two moves the parse turns on: `export const meta` becomes a plain `const`, so the file is no longer module syntax, and the `async` function body makes the top-level `await` these scripts use legal — not their top-level `return`, which the CommonJS parse the `.cjs` extension selects admits anyway. `sed` writes to a file rather than piping into the brace group so its own exit status gates the chain — piped, an unreadable `<file>` is masked, because the shell reports the pipeline's *last* status and the brace group wraps empty input happily. `"use strict";` is ours, not an observed runtime property: it only ever rejects more, and a module-loading runtime parses strictly anyway. `mktemp -d` keeps concurrent checks apart (`wf-address-tasks` fans out task worktrees whose agents may each run one, the rule in `wf-review-cycle.js`'s artifact-directory instruction), and a failing run leaves the directory behind: a parse error's line numbers refer to the wrapped file, and an empty `body.js` with no `w.cjs` means `sed` never read the source.

These behaviors were verified on 2026-08-05 with GNU sed 4.9 and Node v24.18.1, under both `bash` and `dash`:

- Exit 0 on each of the three sources, run from the repository root.
- Exit 2 — `sed`'s own status, before `node` runs — from a wrong cwd or a typo'd path.
- Exit 1 on all three with `let OBVIOUSLY_BROKEN = ;` appended.
- A bare `node --check` exits 0 on all three both unchanged and with that same error appended, and fails only when the error is placed before the `export`.
- Both halves of the wrapper are load-bearing: without the `sed`, all three fail with `SyntaxError: Unexpected token 'export'`; without the function body, or with a non-`async` one, all three fail with `SyntaxError: await is only valid in async functions and the top level bodies of modules`. Neither half is what admits their top-level `return` — `printf 'return 1;\n' > r.cjs && node --check r.cjs` exits 0.
- A parameter name colliding with a top-level `const`, `let`, or `class` is itself a parse error — `(async function(args, agent, meta, log){"use strict"; const meta = 1; });` → `SyntaxError: Identifier 'meta' has already been declared` — and after the `sed` all three sources declare exactly such a top-level `const meta`.

A pass is not a promise that the runtime will accept the file: this wrapper stands in for the runtime's wrapping rather than reproducing it. The real parameter list is not derivable here, and by the last measurement that guess is not neutral — a real list containing `meta` would reject what this stand-in accepts. Nothing past parsing is covered either (the `meta`-literal and determinism rules under *Authoring constraints*), so a pass means only that the source is syntactically valid in a shape that admits its top-level `await`.

Check the embedded `review-cycle-core` section for byte-identity after changing it in either file. `wf-address-tasks.js` carries a copy of `wf-review-cycle.js`'s marked section, and the copy is maintained by hand — from the repository root, under `bash` (the process substitutions are not POSIX `sh`):

```
A=$(awk '/BEGIN EMBEDDABLE SECTION: review-cycle-core/,/END EMBEDDABLE SECTION: review-cycle-core/' plugins/dev-skills/workflows/wf-review-cycle.js) \
  && B=$(awk '/BEGIN EMBEDDABLE SECTION: review-cycle-core/,/END EMBEDDABLE SECTION: review-cycle-core/' plugins/dev-skills/workflows/wf-address-tasks.js) \
  && { [ -n "$A" ] && [ -n "$B" ] || { echo 'MARKERS MISSING — one or both extractions are empty'; false; }; } \
  && diff <(printf '%s\n' "$A") <(printf '%s\n' "$B")
```

Empty output — the whole chain exiting 0 — establishes that the two sections are byte-identical, marker lines included, so an edit to one was carried to the other rather than left behind in the file it was made in. The emptiness gate is why the chain is longer than a bare `diff` of the two `awk` extractions: with both marker ranges missing or renamed, both extractions are empty, `diff` compares nothing and exits 0, so the bare form's pass is vacuous exactly when the section has been lost. The gate turns that case into `MARKERS MISSING` and a non-zero status.

It establishes nothing past that: byte-identity proves the text was *copied*, not that it renders. A section whose prompts lost the destroy boundary is identically wrong in both files and passes this check unmoved, which is what the rendering suite below is for.

It also covers the packet hard-check's measuring half, which task 025a added: a pass's `clean` is its own word about its own worktree — and the failure the check exists to contain, a packet returned mid-rebase or mid-cherry-pick, prints empty porcelain — so the cycle takes its own reading, `git status --porcelain` plus the operation-state markers, through a low-effort read-only turn told nothing about the pass it judges, and refuses the packet when that reading disagrees or cannot be taken at all. The reading is taken when the packet RETURNS rather than folded into the next reviewer round, because three of the four conclusions have no reviewer round after the pass they conclude on — the final confirmation pass first among them — so a reviewer-borne reading would leave every one of them unmeasured, and on the rounds it did cover it would arrive only once the reviewer and peer had already been spent on a worktree nobody could trust. Both directions are pinned, on both legs: a measured-dirty or mid-operation packet is refused with the failing condition named (the mid-operation case on the final confirmation pass, whose porcelain is empty), a reading that could not be taken is refused as unknown rather than passing as clean, and a measured-clean cycle concludes exactly as before, carrying one `packetChecks` entry per adopted pass on every exit including the stopped ones.

The measurer's brief is pinned not to forbid the reading it is sent to take: a rebase and a bisect leave HEAD detached, so `git branch --show-current` prints empty, and the branch assertion every other role's worktree contract carries would order the measurer to stop in exactly the states the step exists to find. The section drops that assertion for this role, and the suite checks both halves — the rendered brief on both legs, and, once and outside the section, `wf-address-tasks.js`'s own per-role contracts, since a consumer with a worktree lifecycle supplies its own text and never reaches the section's default.

That batch leg is pinned on a second property the section's default gets for free, its worktree path being fixed: the measurer FINDS its worktree in `git worktree list --porcelain` and never resolves one with `wt-enter`. Every such helper is rerun-safe by design — where the worktree is gone it attaches the branch in a fresh checkout — so a resolving measurer would take its reading from a tree built moments ago, which reads clean whatever the tree the pass returned from held. A registration names the path in every state the tree can be in, `detached` included, so nothing has to be read out of a refusal message either; a worktree that is no longer registered is reported as unknown rather than rebuilt.

Three properties hold that gate up and each is a separate way to lose it: the off-shoot exemption is keyed on the two BRANCH NAMES, so a run on a local off-shoot proceeds whatever the gather reported (keyed on the outcome instead, a same-branch run whose agent misreports `not-applicable` would bypass reconciliation); a run on the PR's own branch continues on `work` and `fast-forwarded` and fails closed on everything else, including an outcome string the script does not know, an empty one and an absent report; and the gate sits ahead of the empty-`items` no-op, because the rule's third outcome returns no items by contract and would otherwise be reported as "nothing to address". The RULE those outcomes come from is the gather brief's, which no scenario reaches because the gather agent is stubbed with a packet already written — so it is read out of the rendered brief instead: both probes, the head they compare against (taken from what the fetch brought, since the recorded OID is normally reachable from the checkout and so survives an existence test that a moved head should fail), the off-shoot skip that reports `not-applicable`, and the outcome vocabulary, whose agreement with the strings the gate keys on is the coupling nothing else pins (rename one on either side alone and both halves stay internally consistent while every same-branch run stops). The working-location gate that runs just ahead of it is driven through the same harness, and its producer half is read from the same brief: an absent or unrecognized `locationMode` and a worktree mode without an absolute path each stop the run rather than defaulting to the main checkout, and the one branch a run may work on that is NOT the PR's head ref — a local off-shoot — is reached only by the request naming it with `off-shoot`, never inferred from the branch's shape, and the conflicting-PR stop that survives beside that token is pinned as qualified both ways — the addressed PR excluded by its globally unique `url`, never by a number that is scoped to a base repository this answer set spans, and the other head identified by repository plus ref — since an unqualified probe would halt an ordinary run on the PR's own branch. That token's own read is swept in both directions beside it, the two costing differently: every genuine spelling of `off-shoot` must select, since a false negative refuses a supported run outright, while an incidental mention selects too and is pinned as the accepted residual rather than narrowed away. What that location then OWES is pinned beside the gate, since reclaiming happens only where a run finished and a halt is what leaves the tree standing: the blocker exit, which runs ahead of the pair's own validation, names the surviving path in the note a maintainer reads first and reclaims nothing, a blocker raised before any attach reports no path instead of inventing one, and the brief obliges an `ok: false` packet raised after the attach to carry the pair at all — `pr` being otherwise owed only on success is what made the halt the one packet that could drop it. The brief's helper-free attach arms are read there too, each having a clause it fails as written without and none of them observable from a stubbed gather: the fork arm's `git worktree add --detach` carries the mandatory path argument, without which it fails before `gh pr checkout` runs and the default worktree mode never covers a fork PR at all; the registration read (`git worktree list`) is stated ONCE ahead of all three arms rather than for any one of them, so the live `pr-<N>` registration a halted run left is reused rather than added over — `git worktree prune` clears only STALE registrations, so without that read the stable slug's whole point, resuming a halted run, works only where the optional helper exists, and scoping the read to the plain attach alone would exempt the one arm that is always helper-free; the fork arm is stated to take PRECEDENCE over both local-`T` arms, since a prior fork run's `gh pr checkout` leaves a same-named local branch that the local arm would otherwise claim on the re-run; and its landing verification names a consequence, a blocker that attaches and substitutes nothing and gives the rejected tree back, because the identity check runs before any checkout and so cannot see a collision `gh`'s own branch selection creates — and a tree left on the ref that collision produced is the one shape no re-run can clear, the registration read above stopping on it every time. The publication guard rides along, checked in the rendered publish brief for the same reason — it is prose rather than script logic: the proper-ancestor stop must be stated ahead of the lease it would otherwise match. The delegated rebase points that run just after the gate are driven through the same harness, with a scripted rebase report standing in for the agent: the base a point reports becomes the cycle's review base only when it is a FULL commit OID (a movable ref and an abbreviation each stop the run, dispatching nothing), a replay must report its build and tests as PASSING rather than merely failing to deny it, a no-op must be backed by the unchanged tip that evidences it rather than by the flag alone, a successful report must name the `refs/pre-rebase/` recovery ref in full for the branch being rebased AND show it resolving to the tip that rebase started from, a prefix being no evidence that the way back exists at all — those two halves being what every rebase stop's note is built from, so a stop names the ref only where the report established it and otherwise names the namespace to search, a halted rebase stops the run before anything is fixed and leaves what it turns on as an open question with origin `rebase` — at the pre-push point behind the questions the cycle that already passed had raised, oldest first — and `no-rebase` runs neither point while still pinning the commit the gather resolved this run's target to — the branch or commit an explicit `rebase on top of <target>` named, resolved where it was named, else the PR's own base ref; and a gather that omits `rebaseTarget` altogether stops the run rather than being read as "the request named none" — on ANY path, since that one field picks which arm the rebase brief resolves the target by, and on the `no-rebase` path it decides the review base as well. The pre-push point rides the same harness, which for it has to script what the nested cycle RETURNS: a no-op there spends no round, and a replay re-runs the cycle over the rebased tree — on that rebase's own pin, under a cap lowered to what remains of the run's 12-round total (so a first cycle that spent it all stops the run unpublished instead of being granted four more), handed the dispositions that passed as the set to carry forward and as its reviewer's baseline, and giving the superseded cycle's open questions, deviations and round count back out with its own — the two deviation sets folded on the deviation's own text — one both cycles state arriving once with one assessment (the later round's), two different ones both arriving with their own — and the superseded cycle's own delivery-failure record, close-out and artifact directory carried out under `preRebase*` names, the record reaching the PR's summary comment with the one claim the re-verification falsified (a commit no fresh reviewer saw) corrected and the failure intact. The brief that makes an agent pin a commit at all, and abort a conflict it cannot judge rather than return mid-rebase, is read out of the rendered text, and read against the clauses of the canonical nugget it renders for an agent that has read no skill. Both of its target-pinning arms are read there, since where a ref is resolved depends on whose ref it is: the PR's own base ref is fetched from the repository the PR itself is in, while a target the request named outright is resolved in the working location and fetched from nowhere — `git fetch <repository> <refspec>` reading that refspec in the repository operand, so sending an explicit token at the base repository would pin an unrelated same-named branch there or stop a run whose target was on disk all along — and the caller's choice between the two arms is driven as running code rather than only rendered. The suite also reads the `address-review` SKILL.md pair itself — the mirrors nothing else checks — pinning that the `hands-off`+default-rebase flag bullet and the Hands-off mode stop list defer to step 2's halt definition by reference instead of restating its cases, and that no conflict-only restatement of the halt comes back to either mirror: two consecutive review rounds each found such a restatement, the closed enumeration standing in for the open set the halt contract defines, which is what made the deferral structural rather than another phrase-level widening.
