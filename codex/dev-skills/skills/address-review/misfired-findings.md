# Findings a bot posted outside its threads

This file is part of the `address-review` skill, and its step numbers and section names are that skill's `SKILL.md`, beside it.
It is read in full during step 3's gather, when a bot's top-level review or issue comment states findings of its own, when step 3's review listing shows a `suppressed` block, or when it shows a bot's review with a body beside `inline: 0`.
What it calls "above" and "below" is step 3 around the point that sent you here — the unresolved threads already gathered, and the terminal no-op that step ends with — and "the rule above" is step 3's: a top-level review summary or issue comment becomes a standalone item only when the maintainer identifies it as outstanding, or a prior disposition record already holds it.
"The listing" is what step 3's `reviews.sh` printed, one `review=` line per submitted review; its `--help` names every field.

**One more source qualifies on its own: a bot reviewer that misfired and posted findings into a top-level review summary or issue comment instead of threads.**
One route per comment, never both: such a comment is never taken whole under the rule above, even where the maintainer names it — it is split into per-finding items here, the maintainer's naming settling that its findings are taken rather than re-judged by the freshness test below — since a whole-comment item on the url alone beside per-finding items on the url plus ordinal would let one finding be addressed twice, or contradictorily.
Such a finding cannot be replied to or resolved, but it is still the review this run was summoned to address, so take each one as a standalone item where it is **fresh and applicable** — all of: it was written against the code you are addressing — the review's `commit` in the listing, which is the REST review object's `commit_id` beside the `url` permalink and the `bot` flag that the Summary comment and the disposition record need (`gh pr view --json reviews` names the commit `commit.oid` and carries neither, so a test written against `commit_id` there matches nothing and misfiles every such finding as stale), or for an issue comment the head its body names (a bot usually states the commit it reviewed; one naming no head is the ambiguous case below, and `created_at` cannot stand in for it: a review begun against the previous head lands after the push that replaced it and still describes the old code), is the current head, or is an earlier head and the file the finding cites is unchanged since, which a suppressed entry's `changed: "same"` says and, for a finding in the body's prose, `git diff --quiet <that commit> <head> -- <file>` exiting 0 in the working location; no thread on this PR, resolved or unresolved, already raises it — a comparison that needs the resolved threads too, so fetch them for it alone (`gh-review-threads.sh --all`) while the work items stay the unresolved set gathered above, since a finding an earlier round already closed as a thread is exactly what this excludes; no earlier round disposed it — a prior disposition record that holds it is replayed under the rule above rather than taken here, and an earlier Summary comment that lists it under "Top-level findings", found among the review's `cited` comments, is that round's answer to it, whether a fix, a push-back or a follow-up; no maintainer reply dismisses it — `cited` names the top-level comments that mention the review — and the review's own `state` is not `DISMISSED` — a review dismissed through GitHub's UI keeps its body, its `commit_id` and the code it names, so nothing else here trips on it, and that dismissal is the maintainer discarding every finding in it; and the code it names still exists on the branch.
A finding failing any of those is stale context and stays out.
One left out only because its file changed since the superseded head it was written against is named with that reason in the Summary comment — or in step 8's report where the run ends as the terminal no-op below — so the maintainer sees it was read rather than missed.
Where a suppressed entry's `changed` is `unknown`, the review's commit is not in this repository: fetch that commit and run the listing again, and where it cannot be had the finding's freshness is ambiguous.
Where it is only ambiguous which of the bot's comments are fresh, take none and say so in the Summary comment — or in step 8's report where the run ends as the terminal no-op below, which posts none — rather than re-addressing a round that is done.
Its disposition rides the Summary comment alone, per step 7, and its identity is the comment's permalink **plus its ordinal within that comment** (`<html_url>`, finding N of M, counted in the order the body presents them): every finding one body holds shares the one permalink, so an identity of the url alone could carry only one of them into the disposition record and would collapse the rest.

**A suppressed-comment block is such a body.**
Copilot's review can list, collapsed inside its body, comments it chose not to post inline, and they never become threads.
The listing gives each as an entry of `suppressed.entries` with its `file`, `line` and `text`, and each entry is one finding of that review under the tests above, its ordinal counted with the body's other findings in the order the body presents them.
Where `parsed` is false the block is there and the script could not read it: open the review's `url` and read the block yourself, and never treat it as empty.

**A bot review that claims findings and delivered none is review input that never arrived.**
Its mark is in the listing: a bot's review whose body advertises findings — a count of issues, findings by category, a verdict that changes are needed — beside `inline: 0`, with no suppressed entry and no finding text of its own, where that bot authored no inline comment under another review of the same `commit` either, since a reviewer that posts each inline comment as its own review shows them on sibling lines.
This repository's own review format asks a reviewer for a count of findings in its summary and the findings in threads, so a reviewer that posted the summary and failed on the threads leaves exactly this body.
A bot's issue comment that advertises findings the same way is read the same way; the listing does not hold issue comments, so that one is found by reading them.
There is nothing in such a review to address, so it is no item; it is named instead, with its permalink, the bot, and what the body claimed: under a "Review input that never arrived" heading in the Summary comment, and in step 8's report, which is the only place it is named where the run ends as the terminal no-op below.
Judge only each bot's most recent review this way, and name none that an earlier Summary comment among its `cited` already named.
